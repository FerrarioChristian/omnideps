1. Panoramica e Obiettivo

La Name Resolution è la Fase 2 della pipeline di analisi. Riceve in input una lista di Module con riferimenti di tipo TypeRef::Unresolved (nomi testuali grezzi estratti dal codice sorgente) e produce in output gli stessi moduli con ogni riferimento trasformato in uno dei seguenti stati:

Stato TypeRefSignificatoEsempio
Resolved(path) Nome trovato nel Global Registry — percorso assoluto calcolato ["root", "core", "Veicolo"]
External(path) Nome riconosciuto tramite import ma non presente nel Registry — dipendenza esterna ["external", "db", "Database"]
Failed(path) Tutti i tentativi di risoluzione sono falliti — il nome rimane irrisolto ["UnknownType"]
Primitive(type) Tipo primitivo (Int, Float, Bool, String, Void) — non viene processato dal resolver Primitive(String)

La pipeline completa in analyzer.rs è:

1. Estrazione CST→IR → 2. Name Resolution → 3. Dependency Graph → 4. Summary

2. Architettura: dal Vecchio al Nuovo Approccio

2.1 Il Problema del Vecchio Approccio (Arena + Flat Symbol Table)

La versione precedente del resolver utilizzava un Arena-based Scope Tree (ScopeTree con Vec<ScopeNode>) e una Symbol Table piatta Σ : QN → C. Questo approccio presentava due problemi critici formalizzati nella tesi:

Problema 1: Complessità O(L) dell'hashing

Con la Symbol Table piatta Σ : QN → C, le chiavi erano QualifiedName (vettori di stringhe). L'operazione di hash richiedeva attraversare l'intero vettore — complessità O(L) dove L è la lunghezza del nome qualificato. Per nomi come ["root", "core", "models", "entities", "Veicolo"], ogni lookup pagava il costo di hashare 5 stringhe.

Problema 2: Collisioni di nomi (Name Clashing)

La Symbol Table piatta conteneva HashMap<Identifier, Component> dove la chiave era il nome semplice ("Veicolo"). Due componenti con lo stesso nome locale in scope diversi collidevano nella stessa mappa. L'Arena doveva navigare fisicamente i nodi per disambiguare — un'operazione O(profondità dell'albero).

2.2 Il Nuovo Approccio: Architettura a 3 Componenti

L'architettura refactored elimina completamente l'Arena Pattern sostituendolo con tre componenti indipendenti e complementari:

Architettura del Resolver Refactored Tre componenti indipendenti, ciascuno con una responsabilità precisa: ┌──────────────────────────────────────────────────────────────────┐ │ │ │ ① GlobalRegistry (src/resolver/registry.rs) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ paths: HashSet<QualifiedName> │ │ │ │ Costruito una sola volta in Pass 1 │ │ │ │ Valida: "Questo percorso assoluto esiste nel progetto?" │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ ② SymbolStack (src/resolver/stack.rs) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ frames: Vec<StackFrame> │ │ │ │ Cresce e si contrae dinamicamente durante il traversal │ │ │ │ Ogni frame = {symbols: HashMap, imports: Vec<Import>} │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ ③ ResolutionCache (src/resolver/cache.rs) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ store: HashMap<String, HashMap<QN, ResolutionResult>> │ │ │ │ Chiave esterna = ScopePath (es. "root::core") │ │ │ │ Memoizzazione O(1) isolata per scope │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ ④ PrimitiveRegistry (src/resolver/primitives.rs) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ lang_primitives: HashSet<String> │ │ │ │ Caricato via JSON a compile-time (Data-Driven) │ │ │ │ Valida: "Questo token è un tipo primitivo?" │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ └──────────────────────────────────────────────────────────────────┘
Principio chiave: Il GlobalRegistry è una struttura statica (read-only dopo la costruzione); il SymbolStack è dinamico (push/pop durante il traversal); il ResolutionCache è append-only (cresce ma non viene mai ridotto). Le tre strutture hanno cicli di vita completamente diversi, il che semplifica il reasoning sulla correttezza.
GlobalRegistry::build() → push/pop SymbolStack → resolve_name_in_context() → Cache::insert()

3. Pass 1: Global Registry

Riferimento: src/resolver/registry.rs

Il GlobalRegistry è la prima struttura ad essere costruita. Il suo scopo è semplice ma fondamentale: registrare tutti i percorsi assoluti che esistono nel progetto, per poter poi rispondere alla domanda "Questo percorso esiste nell'IR?" in O(1).

3.1 Struttura

pub struct GlobalRegistry {
    pub paths: HashSet<QualifiedName>,   // Insieme di tutti i percorsi assoluti nel progetto
}

A differenza della vecchia HashMap<Identifier, Component>, il Registry usa un HashSet — non ha bisogno di associare valori, solo di verificare l'esistenza.

3.2 Costruzione: GlobalRegistry::build

Riferimento: mod.rs:24-30

pub fn build(modules: &[Module]) -> Self {
    let mut registry = Self { paths: HashSet::new() };
    for m in modules {
        registry.register_module(m, vec![]);  // Prefisso iniziale vuoto
    }
    registry
}

La funzione itera su tutti i moduli top-level e chiama register_module ricorsivamente con un prefisso inizialmente vuoto.

3.3 Registrazione ricorsiva: register_module

Riferimento: mod.rs:32-72

Per ogni modulo, la funzione registra:

Passo 1 — Il modulo stesso

prefix.extend(m.name.clone());       // es. [] + ["root"] = ["root"]
self.paths.insert(prefix.clone());   // Registra ["root"]

Passo 2 — Tipi strutturati e loro metodi

    let mut st_prefix = prefix.clone();

        m_prefix.extend(method.name.clone());

Passo 3 — Funzioni libere

for ff in &m.free_functions {
    let mut ff_prefix = prefix.clone();
    ff_prefix.extend(ff.name.clone());   // ["root", "core"] + ["calcola"] = ["root", "core", "calcola"]
    self.paths.insert(ff_prefix);
}

Passo 4 — Metodi degli Impl Blocks

for ib in &m.impl_blocks {
    let target_name = match &ib.impl_for {
        TypeRef::Unresolved(qn) | TypeRef::Resolved(qn) => qn.last().cloned().unwrap_or_default(),
        _ => "".to_string(),

            m_prefix.extend(method.name.clone());
            self.paths.insert(m_prefix);       // ["root", "Veicolo", "new"]

}

I metodi degli impl blocks vengono registrati sotto il tipo target — come se il metodo fosse definito direttamente nella struct.

Passo 5 — Ricorsione nei sotto-moduli

for sub in &m.sub_modules {
    self.register_module(sub, prefix.clone());  // Ricorsione con prefisso accumulato
}

Riferimento: mod.rs:74-76

4. L'Environment (ρ): Il Symbol Stack

Riferimento: src/resolver/stack.rs:1-67

Dalla formalizzazione LaTeX, l'Environment è definito come:

Definizione formale: ρ = ⟨Σ₀, Σ₁, ..., Σₙ⟩ dove ogni frame Σₖ = ⟨Symbols, Iimports⟩. Lo stack cresce verso l'alto — Σₙ è il frame corrente (top), Σ₀ è il frame globale (bottom).

4.1 StackFrame — Il singolo frame lessicale

pub struct StackFrame {
    /// Simboli locali: nome semplice → percorso assoluto QualifiedName
    pub symbols: HashMap<String, QualifiedName>,
    /// Jump points (import/use statements) disponibili in questo scope
    pub imports: Vec<Import>,
}
Differenza fondamentale dal vecchio approccio: Nel vecchio ScopeNode, la mappa symbols era HashMap<Identifier, Component> — associava il nome a un intero componente IR. Nel nuovo StackFrame, la mappa è HashMap<String, QualifiedName> — associa il nome locale al suo percorso assoluto. Il frame non possiede i componenti, conosce solo dove trovarli.

4.2 SymbolStack — Lo stack dinamico

pub struct SymbolStack {
    pub frames: Vec<StackFrame>,   // Lo stack: frames[0] = bottom, frames[last] = top
}

4.3 API del SymbolStack

MetodoFunzioneRiferimento

pop_scope() Rimuove e distrugge il frame in cima allo stack. Chiamato quando il traversal esce da uno scope. Tutti i simboli e import del frame vengono persi. stack.rs:39-41

4.4 Ciclo di vita: crescita e contrazione durante il traversal

Lo stack si espande quando il resolver entra in uno scope e si contrae quando ne esce. Ogni push_scope è bilanciato da un pop_scope:

Fase 1: resolve_type_refs() → push_scope() Stack: [ Frame₀ (GLOBAL ROOT) ] Fase 2: resolve_module_in_context("root") → push_scope() Stack: [ Frame₀, Frame₁ (root — imports + symbols) ] Fase 3: resolve_module_in_context("core") → push_scope() Stack: [ Frame₀, Frame₁, Frame₂ (core — symbols) ] Fase 4: resolve_structured_type("Veicolo") → push_scope() Stack: [ Frame₀, Frame₁, Frame₂, Frame₃ (Veicolo) ] ... risoluzioni dei TypeRef dentro Veicolo ... Fase 5: pop_scope() ← esce da Veicolo Stack: [ Frame₀, Frame₁, Frame₂ ] Frame₃ distrutto Fase 6: resolve_structured_type("Auto") → push_scope() Stack: [ Frame₀, Frame₁, Frame₂, Frame₃' (Auto) ] Nuovo frame! ... e così via ...
Vantaggi rispetto all'Arena: Lo stack non alloca mai nodi permanenti — i frame vivono solo per la durata del traversal del loro scope. L'Arena vecchia manteneva tutti i nodi in memoria per l'intera durata dell'analisi, anche dopo che lo scope era stato completamente processato. Lo stack usa meno memoria in ogni istante: la sua dimensione massima è pari alla profondità massima dell'albero dei moduli, non al numero totale di nodi.

5. Il Resolution Cache

Riferimento: src/resolver/cache.rs:1-45

5.1 Struttura

pub struct ResolutionCache {
    /// Maps Scope Path → (Name Searched → Resolution Result)
    store: HashMap<String, HashMap<QualifiedName, ResolutionResult>>,
}

La cache ha una struttura a due livelli:

  1. Livello esterno: la chiave è una stringa che rappresenta il percorso dello scope corrente (es. "root::core").
  2. Livello interno: la chiave è il nome cercato (QualifiedName), il valore è il ResolutionResult.

5.2 La funzione scope_key

Riferimento: cache.rs:22-28

fn scope_key(prefix: &[String]) -> String {
    if prefix.is_empty() {
        "GLOBAL_ROOT".to_string()    // Lo scope radice senza prefisso
    } else {
        prefix.join("::")            // Es: ["root", "core"] → "root::core"
    }
}
Il concetto di Cache Tree dalla tesi LaTeX: La formalizzazione definisce il Cache Tree come Ctree : (ScopePath) → (QN → ResolutionResult). Nella vecchia implementazione, la chiave era una tupla (usize, QualifiedName) dove usize era l'indice dell'Arena. Nella nuova implementazione, si usa il percorso dello scope come stringa — questo elimina la dipendenza dall'Arena e isola la memoizzazione per scope path, garantendo che lo stesso nome risolto da scope diversi produce entry separate.

5.3 Operazioni

// Lettura — O(1) amortizzato
pub fn get(&self, current_prefix: &[String], name: &QualifiedName) -> Option<ResolutionResult> {
    let key = Self::scope_key(current_prefix);
    self.store.get(&key).and_then(|scope_cache| scope_cache.get(name).cloned())
}

// Scrittura — O(1) amortizzato
pub fn insert(&mut self, current_prefix: &[String], name: QualifiedName, res: ResolutionResult) {
    let key = Self::scope_key(current_prefix);
    self.store.entry(key).or_insert_with(HashMap::new).insert(name, res);
}
Esempio di struttura della cache a runtime: store = { "GLOBAL_ROOT" → { }, ← scope radice, solitamente vuoto "root" → { ["User"] → Local(["root", "User"]), }, "root::core" → { ["Veicolo"] → Local(["root", "core", "Veicolo"]), ["Auto"] → Local(["root", "core", "Auto"]), }, "root::core::Auto" → { ["Veicolo"] → Local(["root", "core", "Veicolo"]), ["Db"] → External(["external", "db", "Database"]), }, }
Nota: Solo i risultati con successo (Local o External) vengono inseriti nella cache. Se resolve_name_in_context restituisce None, il risultato non viene cachato — la risoluzione Failed viene assegnata dal wrapper resolve_type_ref, non dall'algoritmo di risoluzione.

6. Il ResolutionContext

Riferimento: src/resolver/mod.rs:80-85

pub struct ResolutionContext<'a> {
    pub current_prefix: QualifiedName,          // Prefisso accumulato (es. ["root", "core"])
    pub stack: &'a RefCell<SymbolStack>,        // Riferimento allo stack condiviso
    pub cache: &'a RefCell<ResolutionCache>,    // Riferimento alla cache condivisa
    pub registry: &'a GlobalRegistry,           // Riferimento al registry (read-only)
}

Il ResolutionContext è il "collante" che unisce i tre componenti dell'architettura. Viene passato a ogni funzione di risoluzione e viene ricreato ad ogni livello di discesa (con un nuovo current_prefix), mantenendo gli stessi riferimenti allo stack, cache e registry.

Perché RefCell? Lo stack e la cache devono essere mutati durante la risoluzione, ma il contesto viene condiviso tra più risoluzioni (es. tutti i campi di una struct vengono risolti con lo stesso contesto). RefCell permette la mutazione interiore — il contesto è passato come riferimento immutabile &ctx, ma lo stack e la cache possono essere modificati tramite borrow_mut(). Il Registry, essendo read-only, usa un riferimento normale &'a GlobalRegistry.

6.1 ResolutionResult — L'esito della risoluzione

Riferimento: mod.rs:10-14

pub enum ResolutionResult {
    Local(QualifiedName),     // Trovato nel GlobalRegistry → componente interno al progetto
    External(QualifiedName),  // Import verificato ma non presente nel Registry → dipendenza esterna
}

Se nessuna delle due varianti viene prodotta, il TypeRef verrà marcato come Failed.

7. L'Algoritmo di Risoluzione: resolve_name_in_context

Riferimento: src/resolver/mod.rs:114-212

Questa è la funzione cuore dell'intero sistema. Riceve un contesto e un nome da risolvere (es. ["Veicolo"] o ["db", "Config"]) e restituisce Option<ResolutionResult>.

L'algoritmo segue una catena di priorità precisa:

0. Cache → 1. Lexical Climb → 1A. Local Symbols → 1B. Imports (alias/name/wildcard) → 2. Absolute Fallbacks → None (Failed)

Il passaggio 1 è un loop che itera i frame dello stack dall'alto verso il basso (Lexical Climb). Per ogni frame, controlla prima i simboli locali (1A), poi gli import (1B). Il passaggio 2 viene eseguito solo se il loop termina senza successo.

Step 0 — Memoization (Cache Lookup)

Righe 121-124

if let Some(res) = ctx.cache.borrow().get(&ctx.current_prefix, name) {
    return Some(res);
}

Prima di qualsiasi calcolo, controlla se il nome è già stato risolto dallo stesso scope in precedenza. La chiave della cache è il current_prefix (percorso dello scope) + il nome da risolvere. Se trova un risultato, lo restituisce immediatamente — O(1).

La closure validate_import

Righe 126-147

Prima del loop, viene definita una closure riutilizzabile che valida un candidato risolto tramite import:

let validate_import = |candidate: &QualifiedName| -> ResolutionResult {
    if ctx.registry.exists(candidate) {
        ResolutionResult::Local(candidate.clone())         // 1. Esiste direttamente
    } else {
        let mut root_cand = vec!["root".to_string()];
        root_cand.extend(candidate.clone());
        if ctx.registry.exists(&root_cand) {
            ResolutionResult::Local(root_cand)             // 2. Esiste con "root" preposto
        } else if candidate.first() == Some(&"crate".to_string()) {
            let mut crate_cand = vec!["root".to_string()];
            crate_cand.extend(candidate.iter().skip(1).cloned());
            if ctx.registry.exists(&crate_cand) {
                ResolutionResult::Local(crate_cand)        // 3. "crate" → "root"
            } else {
                ResolutionResult::External(candidate.clone())  // 4. External
            }
        } else {
            ResolutionResult::External(candidate.clone())  // 4. External
        }
    }
};

La catena di validazione per gli import segue 4 livelli di fallback:

Lookup diretto → Preponi "root" → Sostituisci "crate" → "root" → External

Step 1 — Lexical Climb (iterazione dei frame top-down)

Righe 149-194

for frame in ctx.stack.borrow().iter_frames_top_down() {
    // Per ogni frame, dal più interno al più esterno...
}

Questo loop implementa il Lexical Climb: itera i frame dello stack dal top (scope più interno) verso il bottom (scope globale). Per ogni frame, prova due strategie:

1A — Simboli Locali nel frame

Righe 151-161

if let Some(abs_path) = frame.symbols.get(first_part) {
    let mut full_path = abs_path.clone();
    full_path.extend(name.iter().skip(1).cloned());   // Aggiunge segmenti rimanenti

    if ctx.registry.exists(&full_path) {
        let res = ResolutionResult::Local(full_path);
        ctx.cache.borrow_mut().insert(&ctx.current_prefix, name.clone(), res.clone());
        return Some(res);    // ✓ Trovato!
    }
}

Se il primo segmento del nome (es. "Veicolo") corrisponde a un simbolo locale del frame, costruisce il percorso assoluto concatenando il percorso registrato nel frame con eventuali segmenti rimanenti del nome, e valida il risultato con il GlobalRegistry.

1B — Import (Jump Points) nel frame

Righe 163-193

Se i simboli locali non producono un match, il sistema scorre gli imports del frame. Ci sono tre sotto-casi:

Import con Alias

if let Some(alias) = &imp.alias {
    if alias == first_part {
        let mut candidate = imp.path.clone();           // ["external", "db", "Database"]
        candidate.extend(name.iter().skip(1).cloned()); // + segmenti dopo l'alias
        let res = validate_import(&candidate);
        // Cache insert + return
    }
}

Import senza Alias (match sull'ultimo segmento)

if let Some(last_part) = imp.path.last() {
    if last_part == first_part {
        let mut candidate = imp.path.clone();           // ["std", "vec", "Vec"]
        candidate.extend(name.iter().skip(1).cloned()); // + segmenti dopo "Vec"
        let res = validate_import(&candidate);
        // Cache insert + return
    }
}

Import Wildcard

// Wildcard import: preponi il path dell'import all'INTERO nome
let mut candidate = imp.path.clone();   // Es: ["java", "util"]
candidate.extend(name.clone());         // + ["ArrayList"] → ["java", "util", "ArrayList"]
let res = validate_import(&candidate);
if let ResolutionResult::Local(_) = res {
    // Cache insert + return SOLO se Local
}
Differenza critica per i wildcard: A differenza degli import normali, i wildcard restituiscono solo se il risultato è Local. Se il candidato è External, l'algoritmo continua a cercare nei frame successivi. Questo evita che un wildcard import esterno "catturi" nomi che potrebbero essere risolti localmente in un frame più esterno.

Step 2 — Fallback Assoluti (Post-Loop)

Righe 196-211

Se il Lexical Climb è terminato senza successo (nessun frame contiene il nome), l'algoritmo tenta due ultime strategie:

2a — Ricerca assoluta diretta

if ctx.registry.exists(name) {
    let res = ResolutionResult::Local(name.clone());
    ctx.cache.borrow_mut().insert(&ctx.current_prefix, name.clone(), res.clone());
    return Some(res);
}

Interpreta il nome come un percorso assoluto che esiste già nel Registry. Gestisce casi come ["root", "core", "Veicolo"] dove il nome passato è già completo.

2b — Preponi "root" al percorso

let mut root_cand = vec!["root".to_string()];
root_cand.extend(name.clone());
if ctx.registry.exists(&root_cand) {
    let res = ResolutionResult::Local(root_cand);
    ctx.cache.borrow_mut().insert(&ctx.current_prefix, name.clone(), res.clone());
    return Some(res);
}

Se il nome non inizia con "root" ma potrebbe essere relativo alla radice del progetto, prova ad aggiungere "root" come prefisso. Es: ["core", "Veicolo"] diventa ["root", "core", "Veicolo"].

Fallimento finale

None   // Nessun candidato trovato → verrà marcato TypeRef::Failed

7.1 Applicazione ai TypeRef: resolve_type_ref

Riferimento: mod.rs:214-228

fn resolve_type_ref(ctx: &ResolutionContext, tr: TypeRef) -> TypeRef {
    match tr {
        TypeRef::Unresolved(qn) => {
            if let Some(res) = resolve_name_in_context(ctx, &qn) {
                match res {
                    ResolutionResult::Local(abs_qn)  => TypeRef::Resolved(abs_qn),  // ✓
                    ResolutionResult::External(ext_qn) => TypeRef::External(ext_qn), // ⬡
                }
            } else {
                if qn.len() == 1 && ctx.primitives.is_primitive(&qn[0]) {
                    TypeRef::Primitive(PrimitiveType::Other(qn[0].clone())) // ⚙
                } else {
                    TypeRef::Failed(qn)   // ✗ Irrisolto
                }
            }
        }
        _ => tr,   // Primitive, già Resolved, già External → non toccare
    }
}

Solo i TypeRef::Unresolved vengono processati. Tutti gli altri stati passano inalterati — la risoluzione è idempotente. Inoltre, grazie all'uso del PrimitiveRegistry caricato a compile-time (Data-Driven JSON), l'analizzatore identifica correttamente tipi come String, int o size_t senza produrre finti fallimenti.

8. Attraversamento Ricorsivo dell'IR

L'attraversamento dell'IR segue un pattern comune: per ogni componente (modulo, struct, funzione, impl block), il resolver crea un nuovo contesto, push un nuovo frame sullo stack, hoista i componenti locali nel frame, risolve i TypeRef, e infine pop il frame.

8.1 resolve_module_in_context

Riferimento: mod.rs:232-323

Per ogni modulo, il resolver:

  1. Estende il prefisso: new_prefix = ctx.current_prefix + module.name
  2. Crea un nuovo contesto con il prefisso aggiornato (stesso stack, cache, registry).
  3. PUSH scope: aggiunge un nuovo frame allo stack.
  4. Hoista gli import: registra tutti gli imports del modulo nel frame corrente.
  5. Hoista i simboli locali:
    • Per ogni StructuredType: define_symbol(nome, percorso_assoluto)
    • Per ogni Function libera: define_symbol(nome, percorso_assoluto)
    • Per ogni sotto-modulo: define_symbol(nome, percorso_assoluto)
  6. Risolve ricorsivamente tutti i componenti.
  7. Flatten degli impl blocks (vedi Sezione 9).
  8. POP scope: rimuove il frame dallo stack.
// Pattern di hoisting (mod.rs:252-267)
for st in &module.structured_types {
    let mut st_path = new_prefix.clone();
    st_path.extend(st.name.clone());
    new_ctx.stack.borrow_mut().define_symbol(st.name.last().unwrap().clone(), st_path);
}
for ff in &module.free_functions {
    let mut ff_path = new_prefix.clone();
    ff_path.extend(ff.name.clone());
    new_ctx.stack.borrow_mut().define_symbol(ff.name.last().unwrap().clone(), ff_path);
}
for sub in &module.sub_modules {
    let mut sub_path = new_prefix.clone();
    sub_path.extend(sub.name.clone());
    new_ctx.stack.borrow_mut().define_symbol(sub.name.last().unwrap().clone(), sub_path);
}
Perché l'hoisting? L'hoisting è il processo di registrare tutti i componenti di uno scope prima di iniziare a risolvere i TypeRef. Questo garantisce che i riferimenti "forward" funzionino: se Auto ha un campo di tipo Veicolo, e Veicolo è definito dopo Auto nel sorgente, l'hoisting assicura che "Veicolo" sia già nel frame quando Auto viene risolto.

8.2 resolve_structured_type

Riferimento: mod.rs:325-384

Per ogni tipo strutturato (struct, class, interface, trait):

  1. Estende il nome con il prefisso corrente.
  2. PUSH scope per il tipo strutturato.
  3. Auto-registra self e this nello scope corrente puntandoli alla struct stessa (tramite register_self_keywords).
  4. Hoista i tipi annidati e i metodi nel frame.
  5. Risolve ogni TypeRef in:
    • super_types — i tipi da cui eredita o che implementa
    • fields — il tipo di ogni campo
    • methods — parametri, return type e body (tramite resolve_function → resolve_block) di ogni metodo
    • nested_types — tipi annidati (ricorsione)
  6. POP scope.

8.3 resolve_function

Riferimento: mod.rs:386-424

Per ogni funzione (sia libera che metodo), la nuova implementazione crea uno scope lessicale, registra i parametri come simboli e delega la risoluzione del body a resolve_block:

  1. Estende il nome con il prefisso corrente.
  2. PUSH scope per la funzione.
  3. Risolve i parametri e li registra come simboli: per ogni parametro, risolve il suo TypeRef e, se il parametro ha un nome e il tipo è stato risolto con successo (TypeRef::Resolved), chiama define_symbol(nome_parametro, percorso_assoluto_tipo) nel frame corrente. Questo permette di risolvere variabili locali il cui tipo dipende da un parametro.
  4. Risolve signature.return_type — il tipo di ritorno.
  5. Delega al body: se la funzione ha un body (Option<Block>), chiama resolve_block(ctx, block) per risolvere le dichiarazioni locali, le chiamate e le istanziazioni.
  6. POP scope.
fn resolve_function(ctx: &ResolutionContext, mut ff: Function) -> Function {
    let mut new_prefix = ctx.current_prefix.clone();
    new_prefix.extend(ff.name.clone());
    ff.name = new_prefix.clone();

    ctx.stack.borrow_mut().push_scope();

    // Risolve parametri E li definisce come simboli nello scope
    ff.signature.parameters = ff.signature.parameters.into_iter().map(|mut p| {
        p.ty = resolve_type_ref(ctx, p.ty);
        if let Some(name) = &p.name {
            if let TypeRef::Resolved(abs_path) | TypeRef::External(abs_path) = &p.ty {
                ctx.stack.borrow_mut().define_symbol(name.clone(), abs_path.clone());
            }
        }
        p
    }).collect();

    ff.signature.return_type = resolve_type_ref(ctx, ff.signature.return_type);

    // Delega la risoluzione del body a resolve_block
    ff.body = ff.body.map(|b| resolve_block(ctx, b));

    ctx.stack.borrow_mut().pop_scope();
    ff
}
Formalizzazione LaTeX: La funzione è ora formalizzata come 𝓕 = ⟨id ∈ 𝒬𝒩, σ, 𝓑?⟩ dove 𝓑? è il body opzionale di tipo Block. La vecchia definizione aveva calls e instantiates direttamente nella Function; ora sono incapsulati nel Block.
Registrazione dei parametri: La registrazione dei parametri come simboli nello scope è un'aggiunta importante rispetto alla versione precedente. Nel vecchio approccio, le funzioni non registravano i parametri — creavano solo uno scope vuoto. Ora, se una funzione ha un parametro v: Veicolo, il nome "v" viene associato al percorso assoluto di Veicolo nello scope della funzione. Questo permette al body di risolvere variabili locali il cui tipo è stato derivato dai parametri.

8.3b resolve_block — Blocchi lessicali annidati

La nuova struttura Block nell'IR rappresenta un blocco lessicale all'interno di una funzione. La struct Function non ha più campi calls e instantiates diretti — questi sono ora incapsulati nel Block:

pub struct Block {
    pub declarations: Vec<Field>,    // Variabili locali (riusa Field: nome + tipo)
    pub calls: Vec<TypeRef>,          // Tipi i cui metodi vengono invocati
    pub instantiates: Vec<TypeRef>,   // Tipi istanziati
    pub sub_blocks: Vec<Block>,       // Blocchi annidati (if, while, scope anonimi)
}

pub struct Function {
    pub name: QualifiedName,
    pub signature: Signature,
    pub body: Option<Block>,          // Sostituisce i vecchi calls/instantiates
}
Formalizzazione LaTeX: Il Block è formalizzato come 𝓑 = ⟨F⃗local, τ⃗calls, τ⃗inst, 𝓑⃗sub⟩ — un vettore di dichiarazioni locali, un vettore di tipi chiamati, un vettore di tipi istanziati e un vettore di sotto-blocchi ricorsivi.

La funzione resolve_block crea uno scope lessicale per ogni blocco:

fn resolve_block(ctx: &ResolutionContext, mut block: Block) -> Block {
    ctx.stack.borrow_mut().push_scope();

    // 1. Risolve le dichiarazioni locali e le registra nello stack
    block.declarations = block.declarations.into_iter().map(|mut decl| {
        decl.ty = resolve_type_ref(ctx, decl.ty);
        if let TypeRef::Resolved(abs_path) | TypeRef::External(abs_path) = &decl.ty {
            ctx.stack.borrow_mut().define_symbol(decl.name.clone(), abs_path.clone());
        }
        decl
    }).collect();

    // 2. Risolve le dipendenze comportamentali
    block.calls = block.calls.into_iter()
        .map(|c| resolve_type_ref(ctx, c)).collect();
    block.instantiates = block.instantiates.into_iter()
        .map(|i| resolve_type_ref(ctx, i)).collect();

    // 3. Ricorsione nei sotto-blocchi
    block.sub_blocks = block.sub_blocks.into_iter()
        .map(|b| resolve_block(ctx, b)).collect();

    ctx.stack.borrow_mut().pop_scope();
    block
}

Il pattern è analogo a resolve_module_in_context: push dello scope, registrazione dei simboli locali (dichiarazioni), risoluzione dei TypeRef, ricorsione nei sotto-blocchi, e infine pop dello scope. Ogni blocco annidato (es. un if, while o uno scope anonimo {}) crea un proprio scope lessicale, garantendo che le variabili dichiarate all'interno non "fuoriescano" dal blocco.

Dichiarazioni come simboli: Quando una dichiarazione locale come let a: Auto = ... viene risolta, il nome "a" viene registrato nello scope del blocco con il percorso assoluto del tipo (["root","core","Auto"]). Questo consente ai blocchi successivi o alle espressioni nello stesso blocco di risolvere riferimenti a "a" tramite il Lexical Climb. Notare che vengono registrati non solo i tipi Resolved, ma anche quelli External, per garantire la visibilità di variabili locali che fanno uso di dipendenze esterne al progetto.

8.4 resolve_impl_block

Riferimento: mod.rs:426-452

Per ogni blocco impl:

  1. Estende il nome con il prefisso corrente.
  2. PUSH scope temporaneo.
  3. Risolve impl_for — il tipo per cui si implementa.
  4. Risolve implements_trait — l'eventuale trait implementato.
  5. Risolve tutti i methods e i nested_types.
  6. POP scope.

9. Flattening degli Impl Blocks

Riferimento: mod.rs:290-311

Dopo che tutti gli impl blocks di un modulo sono stati risolti, avviene una fase cruciale di fusione: i metodi e i tipi annidati definiti negli impl blocks vengono trasferiti direttamente nel StructuredType target.

let mut unfused_impls = vec![];
for ib in resolved_impls {
    let mut fused = false;
    if let TypeRef::Resolved(target_name) = &ib.impl_for {
        if let Some(target_st) = module.structured_types.iter_mut()
            .find(|st| &st.name == target_name)
        {
            target_st.methods.extend(ib.methods.clone());        // Fonde i metodi
            target_st.nested_types.extend(ib.nested_types.clone()); // Fonde i tipi annidati
            if let Some(trait_ref) = ib.implements_trait.clone() {
                target_st.super_types.push(trait_ref);           // Aggiunge il trait ai supertypes
            }
            fused = true;
        }
    }
    if !fused { unfused_impls.push(ib); }
}
module.impl_blocks = unfused_impls;  // Solo gli impl non fusi rimangono

Questo passo è fondamentale perché linguaggi come Rust separano la dichiarazione di una struct dalla definizione dei suoi metodi (tramite impl). Dopo il flattening, il StructuredType contiene tutto ciò che gli appartiene.

Differenza dal vecchio approccio: Nella vecchia implementazione, module.impl_blocks veniva svuotato completamente (= vec![]). Nella nuova versione, gli impl blocks non fusi (quelli il cui impl_for è External o Failed, oppure il target non è trovato nel modulo corrente) vengono preservati in unfused_impls. Questo è più corretto — non perde informazione.

Perché il cambio di architettura?

L'Arena Pattern risolveva il problema dell'ownership bidirezionale in Rust (genitore↔figlio) usando indici usize. Ma questo problema era artificiale: il resolver non ha realmente bisogno di navigare l'albero in entrambe le direzioni. Ha solo bisogno di: (1) sapere quali simboli sono visibili nel contesto corrente (→ SymbolStack), (2) validare se un percorso esiste (→ GlobalRegistry), e (3) cachare i risultati (→ ResolutionCache). Lo stack dinamico modella più naturalmente il concetto di Lexical Scoping: quando entri in uno scope, puoi vedere tutto ciò che è sopra; quando esci, lo scope scompare.
