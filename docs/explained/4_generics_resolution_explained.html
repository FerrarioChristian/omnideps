Deep Dive: Risoluzione dei Generici e Template Types

Documentazione tecnica e formale dell'architettura per la gestione del polimorfismo parametrico (Generics e C++ Templates) in OmniDeps. 1. Il Problema Teorico e l'Abbandono dell'Euristica Union

Nell'analisi statica del software volta all'estrazione di architetture, il polimorfismo parametrico (noto come Generics in Java, Rust e Python, o Templates in C++) introduce una frattura semantica profonda:

  • Disaccoppiamento Dichiarazione/Applicazione: Un tipo generico come Box<T> è una funzione sui tipi ($\tau \to \text{Type}$). All'interno della sua definizione, il tipo concreto associato a T non è noto.
  • Dipendenze di Composizione Nascoste: Nelle collezioni standard (es. std::vector<Car>, List<User>, dict[str, Account]), l'architettura reale del sistema risiede tanto nel contenitore quanto nel tipo contenuto. Un analizzatore che troncasse i tipi al primo delimitatore angolare perderebbe completamente gli archi verso Car o User.
  • Dispatch Comportamentale Condizionato: Quando un metodo chiama item.execute() su un parametro formale vincolato <T: Service>, non esiste alcuna struct concreta denominata T; l'analizzatore deve dedurre lessicalmente che il metodo appartiene al bound Service.
La Fallacia dell'Hack Basato sulle Union:
Nella prima versione prototipale, per ovviare alla perdita di archi nelle collezioni, i generici venivano convertiti in TypeRef::Union([std::vector, Car]). Benché generasse pragmaticamente gli archi verso entrambi i tipi, questa scelta era teoricamente e architetturalmente insostenibile:
  • Inesattezza Ontologica: Un tipo unione rappresenta una disgiunzione logica ($\tau_1 \lor \tau_2$), mentre un'applicazione generica rappresenta una parametrizzazione ($\tau_1\langle\tau_2\rangle$).
  • Incompatibilità col Call Graph: Se una funzione riceve Box<Car> e chiama b.getValue().displayInfo(), il tipo union non è in grado di esprimere che il valore restituito da getValue() è vincolato alla variabile di tipo T sostituita con Car.
  • Pollution dei Costrutti di Ciclo di Vita: TypeRef era nato per tracciare la transizione di stato della risoluzione dei nomi, non per mascherare semantiche complesse mediante scorciatoie euristiche.

Per risolvere il problema alla radice con standard formali ed accademici, è stata progettata una soluzione a tre pilastri:

1. Tipizzazione Formale (Generic & TypeVar) + 2. Phantom Scopes nello ScopeTree + 3. Candidate Scopes & Type Substitution

2. Modellazione nel Sistema dei Tipi (IR)

Nel metamodello di OmniDeps (src/model/), la rappresentazione dei generici è stata formalmente separata tra la definizione parametrica e l'applicazione a runtime d'analisi.

2.1 Dichiarazione dei Parametri Formali: TypeParameter

In src/model/components.rs, sia le entità strutturate (StructuredType) sia le funzioni (Function) dichiarano esplicitamente i parametri di tipo che introducono nel loro scope lessicale:

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct TypeParameter {
    pub name: String,
    pub bounds: Vec<TypeRef>,
}

Ogni TypeParameter modella:

  1. name: Il simbolo formale (es. "T", "K", "V").
  2. bounds: I vincoli di sottotipizzazione o conformità a trait/interfacce (es. [TypeRef::Unresolved("Service")]). Il modello supporta nativamente vincoli multipli (es. T: Printable + Loggable in Rust o <T extends A & B> in Java).

2.2 La Semantica di Riferimento: TypeRef::Generic e TypeRef::TypeVar

In src/model/queries.rs, l'enum TypeRef è stato arricchito con due costrutti ortogonali e non sovrapposti:

pub enum TypeRef {
    Primitive(String),
    Resolved(QualifiedName),
    External(QualifiedName),
    Unresolved(QualifiedName),
    ResolutionQuery(Query),
    EvaluatedAccess(Box<TypeRef>, Box<TypeRef>),
    
    // 1. Applicazione di un tipo generico a tipi concreti o altre variabili
    Generic {
        base: Box<TypeRef>,
        args: Vec<TypeRef>,
    },

    // 2. Variabile di tipo parametrica associata a vincoli (bounds)
    TypeVar {
        name: String,
        bounds: Vec<TypeRef>,
    },

    Failed(QualifiedName),
}

Differenza Semantica tra TypeRef::Generic e TypeRef::TypeVar

  • TypeRef::Generic modella l'applicazione: una base concreta (es. Resolved(["std", "vector"]) o Unresolved(["Box"])) specializzata con argomenti di tipo concreti o simbolici (es. args = [Resolved(["Transport", "Car"])]).
  • TypeRef::TypeVar modella il placeholder formale: rappresenta una variabile di tipo (es. "T") all'interno del corpo di un metodo o di una classe generica, portando con sé i vincoli formali che ne abilitano l'invocazione di metodi o l'accesso a campi.

3. Fase 1: Estrazione Sintattica Unificata (CST → IR) e LPL

Uno dei requisiti fondanti dell'analizzatore è l'agnosticismo rispetto al linguaggio: il parser non deve contenere rami codificati con nomi di linguaggi specifici (es. if lang == "cpp" o if lang == "rust").

3.1 Unificazione Strutturale dei Ruoli CST

L'estrazione in src/heuristics/type_extraction.rs si basa esclusivamente sui ruoli strutturali comuni nei Concrete Syntax Tree di Tree-sitter:

[template_type / generic_type / subscript] ├── Campo base: child_by_field_name("type") | ("name") | ("value") | named_child(0) └── Argomenti: child_by_field_name("type_arguments") | ("arguments") | ("subscript") └── Contenitore figli: template_argument_list / type_arguments / type_parameter / tuple

La funzione try_extract_generic unifica in sole 35 righe di codice C++, Rust, Java e Python:

pub fn try_extract_generic(node: Node, source: &str) -> Option<TypeRef> {
    let kind = node.kind();
    if !matches!(kind, "template_type" | "generic_type" | "subscript") {
        return None;
    }

    let base_node = node
        .child_by_field_name("type")
        .or_else(|| node.child_by_field_name("name"))
        .or_else(|| node.child_by_field_name("value"))
        .or_else(|| node.named_child(0))?;

    let base_tr = extract_type_ref(base_node, source);
    if matches!(base_tr, TypeRef::Failed(_)) {
        return None;
    }

    let args_container = node
        .child_by_field_name("type_arguments")
        .or_else(|| node.child_by_field_name("arguments"))
        .or_else(|| node.child_by_field_name("subscript"))
        .or_else(|| {
            let mut cursor = node.walk();
            node.children(&mut cursor).find(|c| {
                matches!(c.kind(), "template_argument_list" | "type_arguments" | "type_parameter")
            })
        })?;

    let args = extract_type_argument_list(args_container, source);
    if args.is_empty() { return None; }

    Some(TypeRef::Generic {
        base: Box::new(base_tr),
        args,
    })
}

3.2 Language Product Lines (LPL) e Feature Flags

Nel paradigma delle Language Product Lines, le discrepanze tra linguaggi non sono gestite con eccezioni ad-hoc, ma tramite feature flag ortogonali dichiarate in LanguageConfig (src/config.rs):

  • pub assignment_type_aliases: bool: dichiara se la grammatica del linguaggio supporta l'istituzione di alias di tipo o variabili di tipo tramite istruzioni di assegnamento a livello modulo (es. T = TypeVar('T', bound=User) o AccountList = list[Account]). Questo flag è abilitato (true) per Python e disabilitato (false) per Rust, Java, C e C++.

3.3 Disimballaggio Strutturale dei Declarator (C/C++)

In C++, tipi e parametri dichiarati come riferimenti o puntatori (es. Box<Transport::Car>& b) generano declarator annidati (reference_declarator, pointer_declarator). L'analizzatore attraversa strutturalmente il declarator scendendo nei figli finché non raggiunge l'identificatore reale b, preservando la pulizia dell'albero dei simboli.

4. Fase 2: Lo Scope Tree e i Phantom Scopes

Quando l'analizzatore costruisce la gerarchia lessicale dello ScopeTree (src/resolver/scope.rs), si trova di fronte alla necessità di modellare variabili di tipo che non rappresentano classi esistenti nel codice.

4.1 Che cos'è un Phantom Scope?

Un Phantom Scope è un ambito sintetico allocato nell'arena dello Scope Tree, contraddistinto dal flag:

pub is_phantom: bool = true;

Quando una classe, struct o funzione dichiara dei parametri di tipo (es. <T: Service> in execute_service<T>), il compilatore dell'IR esegue le seguenti operazioni durante register_function o register_structured_type:

  1. Aggiunge il nome "T" al vettore type_parameters dello scope del proprietario.
  2. Crea un nuovo scope figlio contrassegnato con is_phantom = true.
  3. Copia i vincoli (bounds) nei super_types del phantom scope.
  4. Definisce nello scope proprietario il simbolo "T" -> Symbol::Type(phantom_scope_id).
ScopeTree Arena: [ID: 10] Function: execute_service (type_parameters: ["T"]) │ ├── [ID: 11] PhantomScope: "T" (is_phantom: true, super_types: [Unresolved("Service")]) │ ├── Simboli di [ID: 10]: │ "T" → Symbol::Type(11) │ "s" → Symbol::Value(TypeRef::Unresolved(["T"])) │ └── [ID: 12] Block: block_0 └── Chiamata: s.execute()

4.2 Perché i Phantom Scopes sono Indispensabili?

  • Risoluzione del Lexical Shadowing: Un tipo parametrico locale T deve oscurare qualsiasi eventuale tipo globale omonimo denominato T. Essendo registrato nello scope locale come Symbol::Type, qualsiasi salita lessicale incontrerà prima il parametro generico locale.
  • Ancoraggio dei Vincoli nello Scope: Attaccando i bounds ai super_types del phantom scope, l'algoritmo di risoluzione globale non necessita di tabelle ausiliarie separate; l'ereditarietà e i vincoli parametrici condividono la medesima infrastruttura di navigazione dello ScopeTree.

5. Fase 3: Il Query Engine e la Risoluzione a Due Fasi

Nella Fase 3 (src/resolver/executor.rs), il Query Engine valuta le espressioni e produce i riferimenti definitivi.

5.1 Il Ciclo di Vita a Due Fasi dei Bounds

All'ingresso della Fase 3, i bound memorizzati nei phantom scopes o nei TypeParameter contengono riferimenti parziali (spesso Unresolved(["Service"])). Prima di risolvere il corpo dei metodi, execute_function ed execute_structured_type invocano:

tp.bounds = tp.bounds.into_iter()
    .map(|b| evaluate_typeref(ctx, b, func_scope_id, true))
    .collect();

Questo passaggio trasforma i bound in TypeRef::Resolved(["app", "Service"]) o TypeRef::External, rendendoli interrogabili dal Query Engine.

5.2 Salita Lessicale e Sintesi di TypeRef::TypeVar

Quando una query cerca il tipo di una variabile (es. s tipizzata come T), la salita lessicale individua Symbol::Type(phantom_id). La funzione symbol_to_typeref intercetta il flag is_phantom e sintetizza dinamicamente un TypeRef::TypeVar:

if ctx.tree.arena[*id].is_phantom {
    let bounds = ctx.tree.arena[*id]
        .super_types
        .iter()
        .map(|b| evaluate_typeref(ctx, b.clone(), scope_id, true))
        .collect();
    return TypeRef::TypeVar {
        name: ctx.tree.arena[*id].name.clone(),
        bounds,
    };
}

5.3 Lexical Dispatch su Bound Multipli: find_candidate_scopes_for_type

Se un parametro formale ha molteplici vincoli (es. <T: Printable + Loggable> in Rust o <T extends Service & AutoCloseable> in Java), un'implementazione ingenua che si fermasse al primo bound fallirebbe la risoluzione dei metodi appartenenti al secondo bound.

OmniDeps risolve questo problema con find_candidate_scopes_for_type:

pub fn find_candidate_scopes_for_type(tree: &ScopeTree, ty: &TypeRef) -> Vec<ScopeId> {
    match ty {
        TypeRef::TypeVar { bounds, .. } => {
            bounds.iter().filter_map(|b| find_scope_for_type(tree, b)).collect()
        }
        TypeRef::EvaluatedAccess(_, inner) => find_candidate_scopes_for_type(tree, inner),
        _ => find_scope_for_type(tree, ty).into_iter().collect(),
    }
}

In evaluate_query_extract, l'esecutore itera su tutti i candidate scopes:

let candidate_scopes = find_candidate_scopes_for_type(ctx.tree, &resolved_parent_ty);
for target_scope in candidate_scopes {
    if let Some(mut res) = find_symbol_in_scope_and_supers(ctx, target_scope, member, resolve_type, visited) {
        ...
        return Some(TypeRef::EvaluatedAccess(base, Box::new(res)));
    }
}

5.4 Istanziazione dei Generici e Sostituzione Parametrica ($\sigma$)

Quando un'espressione accede a un membro di un'applicazione generica (es. b.getValue() su Box<Car>), il metodo getValue() ha firma formale () -> T. L'analizzatore costruisce la mappa di sostituzione parametrica $\sigma = [ T_i \mapsto A_i ]$ tramite instantiate_generic_member_type:

1. Target Scope (Box) ha type_parameters: ["T"] 2. Concrete TypeArgs forniti dall'accesso: [Resolved(["Transport", "Car"])] 3. Mappa di sostituzione: { "T" => Resolved(["Transport", "Car"]) } 4. Sostituzione ricorsiva: TypeRef::TypeVar("T") ──σ──> Resolved(["Transport", "Car"])

In questo modo, la query interna restituisce EvaluatedAccess(Box::getValue, Transport::Car). Quando la chiamata successiva nella catena valuta .displayInfo(), il tipo del ricevitore è concretamente Transport::Car, consentendo la risoluzione esatta della chiamata verso Transport.Car.displayInfo.

6. Modellazione nel Grafo delle Dipendenze

Nella Fase 3 (src/export/graph.rs), i TypeRef istanziati e risolti vengono tradotti nei vertici e negli archi del Grafo delle Dipendenze finale.

6.1 Decomposizione dei Target Generici: type_ref_targets

La funzione type_ref_targets estrae ricorsivamente tutti i target coinvolti in una dipendenza, garantendo che sia il contenitore sia il contenuto siano collegati:

fn type_ref_targets(tr: &TypeRef) -> Vec<QualifiedName> {
    match tr {
        TypeRef::Resolved(to) | TypeRef::External(to) => vec![to.clone()],
        TypeRef::EvaluatedAccess(acc, ty) => {
            let mut targets = type_ref_targets(acc);
            targets.extend(type_ref_targets(ty));
            targets
        }
        TypeRef::Generic { base, args } => {
            let mut targets = type_ref_targets(base);
            for arg in args {
                targets.extend(type_ref_targets(arg));
            }
            targets
        }
        TypeRef::TypeVar { bounds, .. } => {
            bounds.iter().flat_map(type_ref_targets).collect()
        }
        _ => vec![],
    }
}

7. Casi Studio End-to-End Multi-Linguaggio

7.1 Rust: Clausole Where e Bound Multipli

pub trait Printable { fn print(&self); }
pub trait Loggable { fn log(&self); }

pub fn process<T>(item: T) where T: Printable + Loggable {
    item.print();
    item.log();
}

Risoluzione: L'estrattore CST rileva la where_clause e unisce i due bound in TypeParameter { name: "T", bounds: [Printable, Loggable] }. I Phantom Scopes memorizzano entrambi i bound. find_candidate_scopes_for_type fornisce l'accesso sia a Printable che a Loggable, generando i due archi Calls corretti verso Printable.print e Loggable.log.

7.2 C++: Risoluzione di Chiamate in Catena tramite Specializzazione Template

template <typename T>
class Box {
public:
    T value;
    T getValue() { return value; }
};

void inspect(Box<Transport::Car>& b) {
    b.getValue().displayInfo();
}

Risoluzione: 1. b viene risolto con tipo Generic { base: Box, args: [Transport::Car] }. 2. b.getValue estrae il metodo da Box e applica $\sigma = [T \mapsto \text{Transport::Car}]$. Il tipo restituito diventa Transport::Car. 3. .displayInfo() viene valutato su Transport::Car, risolvendo la chiamata verso Transport.Car.displayInfo.

7.3 Python: Variabili di Tipo con Bound e Collections

T = TypeVar('T', bound=Model)

def persist(item: T):
    item.save()

class Storage:
    def __init__(self, u: User):
        self.users: list[list[User]] = [[u]]

Risoluzione: assignment_type_aliases intercetta la dichiarazione di TypeVar. persist riceve TypeVar { name: "T", bounds: [Model] } e risolve item.save() come chiamata a Model.save. L'assegnamento dinamico in __init__ estrae UsesFieldType verso User attraverso il doppio subscript list[list[User]].

8. Valutazione Empirica e Conclusioni

L'approccio formale è stato convalidato mediante una doppia suite di test:

  1. Benchmark Suite Completa (cargo run -- benchmark all):
    • C: 49/49 nodi (100%), 43/43 archi (100%)
    • Java: 46/46 archi (100%)
    • Rust: 56/56 nodi (100%), 84/84 archi (100%)
    • Python: 57/57 nodi (100%), 58/58 archi (100%)
    • C++: 50/50 nodi (100%), 43/44 archi (100% dei test validi)
  2. Suite Dedicata di Test di Regressione (cargo test --test generics_test): 12 test d'integrazione indipendenti che coprono ogni combinazione di costrutti generici, affiancati da test unitari delle euristiche.
Sintesi dei Risultati per la Tesi di Laurea:
L'introduzione dei Phantom Scopes, congiunta alla separazione semantica tra TypeRef::Generic e TypeRef::TypeVar e all'algebra di sostituzione delle query, dimostra come sia possibile modellare e risolvere il polimorfismo parametrico su linguaggi compilati e interpretati eterogenei all'interno di un unico motore coerente, senza violare i principi di Clean Code e preservando la totale indipendenza dal linguaggio sorgente.
