1. Panoramica e Architettura

La Fase 1 (Estrazione) è il primo stadio della pipeline di analisi. Riceve in input il codice sorgente di un file e produce in output una lista di Module che costituiscono la Rappresentazione Intermedia (IR) — un modello strutturale del codice che è completamente indipendente dal linguaggio sorgente.

1. Estrazione CST→IR → 2. Name Resolution → 3. Dependency Graph → 4. Summary

Riferimento: analyzer.rs:94-107 — funzione full_analysis()

L'architettura interna della Fase 1 si compone di quattro strati logici, organizzati in modo che ogni strato dipenda solo da quelli sottostanti:

analyzer.rs — Orchestrazione (parsing + walk_cst)
heuristics/mod.rs — Dispatcher (dispatch_node)
heuristics/classifiers.rs + parsers.rs — Classificazione e Parsing
heuristics/text_parsing.rs + structural_extraction.rs + body_extraction.rs — Estrazione dati dal CST

2. Tree-sitter: dal Codice Sorgente al CST

Riferimento: analyzer.rs:6-18

Tree-sitter è un generatore di parser incrementali. Per ogni linguaggio supportato, produce un parser specializzato che trasforma il codice sorgente in un Concrete Syntax Tree (CST) — un albero che rappresenta ogni singolo token del codice, inclusi spazi, punteggiatura e parole chiave.

pub fn generic_extract(lang: Language, source: &str) -> anyhow::Result<Vec<Module>> {
    // 1. Crea un parser Tree-sitter
    let mut parser = tree_sitter::Parser::new();
    parser.set_language(&lang).unwrap();

    // 2. Parsa il codice sorgente → CST
    let tree = parser.parse(source, None)
        .ok_or(anyhow::anyhow!("parse failed"))?;
    let root = tree.root_node();

    // 3. Attraversa il CST per costruire l'IR
    let mut modules = vec![];
    walk_cst(root, source, &mut modules);
    Ok(modules)
}

La funzione detect_language in main.rs mappa le estensioni dei file ai parser Tree-sitter:

EstensioneLinguaggioCrate Tree-sitter

2.2 CST vs AST

Differenza chiave: Un Abstract Syntax Tree (AST) omette i dettagli sintattici (parentesi, punti e virgola, ecc.) e ragiona in termini semantici. Un Concrete Syntax Tree (CST) preserva ogni token del codice — Tree-sitter produce un CST. I nodi CST hanno un kind() (tipo grammaticale, es. "struct_item", "function_definition") e possono avere named fields (es. "name", "body", "parameters") per accedere ai figli con semantica.

2.3 Esempio di CST

Per il codice Rust struct Auto { base: Veicolo }, Tree-sitter produce un albero simile a:

source_file └── struct_item ├── keyword "struct" ├── name: type_identifier "Auto" └── body: field_declaration_list └── field_declaration ├── name: field_identifier "base" └── type: type_identifier "Veicolo"

L'analizzatore usa il kind() dei nodi per classificarli (il nodo struct_item contiene "struct" → è un tipo strutturato) e i named fields per estrarre dati specifici (il campo "name" contiene il nome della struct).

3. La Rappresentazione Intermedia (IR)

Riferimento: ir.rs

L'IR è l'output della Fase 1 e l'input della Fase 2 (Name Resolution). È un modello strutturale indipendente dal linguaggio che cattura la topologia del codice. È composta dalle seguenti strutture principali:

3.1 Module — Il contenitore top-level

pub struct Module {
    pub name: QualifiedName,                   // Es: ["root"] o ["core"]
    pub imports: Vec<Import>,                  // Import dichiarati nel modulo
    pub sub_modules: Vec<Module>,              // Moduli annidati
    pub structured_types: Vec<StructuredType>, // Struct, class, interface, ecc.
    pub free_functions: Vec<Function>,         // Funzioni non legate a un tipo
    pub impl_blocks: Vec<ImplBlock>,           // Blocchi impl (specifici di Rust)
}

3.2 StructuredType — Tipi strutturati

pub struct StructuredType {
    pub name: QualifiedName,                    // Es: ["Veicolo"]
    pub kind: StructuredTypeKind,               // Class | Struct | Interface | Trait
    pub fields: Vec<Field>,                    // Campi della struttura
    pub methods: Vec<Function>,                // Metodi dichiarati nel corpo
    pub super_types: Vec<TypeRef>,             // Tipi da cui eredita/implementa
    pub nested_types: Vec<StructuredType>,     // Tipi annidati
}

3.3 Function — Funzioni e metodi

pub struct Function {
    pub name: QualifiedName,                    // Es: ["calcola"]
    pub signature: Signature {
        pub parameters: Vec<Parameter>,        // Parametri con nome e tipo
        pub return_type: TypeRef,               // Tipo di ritorno
    },
    pub body: Option<Block>,                   // Corpo strutturato della funzione
}

Il campo body contiene un Option<Block> che rappresenta il corpo della funzione in modo strutturato. Il Block cattura le dichiarazioni locali, le dipendenze comportamentali (chiamate e istanziazioni) e i blocchi annidati (if, while, scope anonimi). Se la funzione non ha un body (es. dichiarazioni in header C/C++), il campo è None.

3.4 Block — Blocchi di codice strutturati

pub struct Block {
    pub declarations: Vec<Field>,              // Variabili locali (let, var, ecc.)
    pub calls: Vec<TypeRef>,                   // Funzioni chiamate in questo blocco
    pub instantiates: Vec<TypeRef>,            // Tipi istanziati in questo blocco
    pub sub_blocks: Vec<Block>,                // Blocchi annidati (if, while, scope)
}

La struttura Block modella la gerarchia dei blocchi di codice all'interno del corpo di una funzione. Ogni blocco contiene:

  • declarations — Variabili locali dichiarate nel blocco (es. let x: i32), estratte come Field { name, ty }.
  • calls — Funzioni e metodi chiamati direttamente nel blocco (non nei sotto-blocchi).
  • instantiates — Tipi istanziati direttamente nel blocco.
  • sub_blocks — Blocchi annidati (es. body di un if, while, scope anonimi { ... }), ognuno rappresentato ricorsivamente come un Block.
Separazione per livello: Le dipendenze (calls/instantiates) di un blocco includono solo quelle trovate al suo livello diretto — le dipendenze nei sotto-blocchi sono registrate nei rispettivi sub_blocks. Questo evita il double-counting e permette un'analisi più precisa degli scope.

3.5 TypeRef — Riferimenti ai tipi

Nella Fase 1, ogni riferimento a un tipo viene estratto come TypeRef::Unresolved. Sarà la Fase 2 a risolverlo:

pub enum TypeRef {
    Primitive(PrimitiveType),   // Int, Float, Bool, String, Void
    Unresolved(QualifiedName),  // Nome estratto ma non ancora risolto ← Fase 1 produce questi
    Resolved(QualifiedName),    // Risolto a percorso assoluto (Fase 2)
    External(QualifiedName),    // Dipendenza esterna (Fase 2)
    Failed(QualifiedName),      // Risoluzione fallita (Fase 2)
}

3.6 Import e ImplBlock

pub struct Import {
    pub path: QualifiedName,        // Es: ["std", "vec", "Vec"]
    pub alias: Option<Identifier>,  // Es: Some("Db")
    pub is_wildcard: bool,          // true per "use std::*"
}

pub struct ImplBlock {
    pub name: QualifiedName,                    // Nome estratto dal nodo
    pub methods: Vec<Function>,                // Metodi dell'impl
    pub impl_for: TypeRef,                      // Il tipo target
    pub implements_trait: Option<TypeRef>,      // Trait implementato (opzionale)
    pub nested_types: Vec<StructuredType>,     // Tipi annidati nell'impl
}

3.7 ParsedItem — L'output del dispatcher

pub enum ParsedItem {
    Component(Component),    // Module, StructuredType, o Function
    ImplBlock(ImplBlock),    // Blocco impl (trattato separatamente)
    Import(Import),          // Dichiarazione di import
}

Questo enum è il tipo di ritorno del dispatcher. Separa gli ImplBlock e gli Import dai Component standard perché richiedono un trattamento speciale durante l'inserimento nell'IR (vedi Sezione 4).

4. L'Attraversamento del CST: walk_cst

Riferimento: analyzer.rs:23-67

La funzione walk_cst è il cuore dell'attraversamento. È una funzione ricorsiva che visita ogni nodo del CST, prova a classificarlo tramite il dispatcher, e gestisce l'inserimento nell'IR in base al tipo riconosciuto.

4.1 Il Modulo "root" Implicito

Alla prima chiamata, il vettore modules è vuoto. Non appena il dispatcher riconosce il primo componente di qualsiasi tipo, viene creato automaticamente un modulo "root" fittizio:

if modules.is_empty() {
    modules.push(Module {
        name: vec!["root".to_string()],
        imports: vec![],
        sub_modules: vec![],
        structured_types: vec![],
        free_functions: vec![],
        impl_blocks: vec![],
    });
}

Tutti i componenti top-level (struct, funzioni, import, ecc. che non sono dentro un modulo esplicito) vengono inseriti in modules[0] — il modulo "root". Questo garantisce che l'IR abbia sempre almeno un modulo contenitore.

4.2 Logica di Attraversamento

Per ogni nodo del CST, walk_cst esegue la seguente logica:

walk_cst(node, source, modules) 1. Chiama dispatch_node(node, source) 2. Se il dispatcher restituisce Some(item): │ ├─ Module → crea un vettore temporaneo con il modulo parsato, │ ri-attraversa i figli del nodo corrente nel contesto del nuovo modulo, │ poi inserisce il modulo popolato in modules[0].sub_modules. │ ├─ StructuredType → inserisce direttamente in modules[0].structured_types. │ (Non attraversa i figli — i metodi/campi sono già stati estratti dal parser) │ ├─ Function → inserisce in modules[0].free_functions, │ poi attraversa i figli solo se sono "body" o "block" │ (per cercare struct/classi definite dentro la funzione) │ ├─ ImplBlock → inserisce in modules[0].impl_blocks. │ └─ Import → inserisce in modules[0].imports. return; // STOP — non scende nei figli (per i casi non-Module/Function) 3. Se il dispatcher restituisce None: └─ Attraversa ricorsivamente tutti i figli del nodo corrente. (Il nodo non è stato riconosciuto, continua a scendere)

4.3 Gestione Speciale dei Moduli

Riga 37-46

Quando il dispatcher riconosce un modulo (es. mod core { ... }), il trattamento è diverso dagli altri componenti:

crate::heuristics::ParsedItem::Component(crate::ir::Component::Module(m)) => {
    // 1. Crea un vettore temporaneo col modulo appena parsato
    let mut new_modules = vec![m];

    // 2. Ri-attraversa i figli del nodo CST nel contesto del NUOVO modulo
    let mut cursor = node.walk();
    for child in node.children(&mut cursor) {
        walk_cst(child, source, &mut new_modules);
    }

    // 3. Inserisce il modulo (ora popolato) come sotto-modulo del root
    modules[0].sub_modules.push(new_modules.remove(0));
}

Questo meccanismo è cruciale: i componenti trovati dentro il nodo del modulo vengono inseriti nel nuovo modulo (tramite new_modules), non nel modulo root. Questo preserva la gerarchia del codice sorgente nell'IR.

Perché new_modules è un Vec? La funzione walk_cst riceve un &mut Vec<Module> — non un singolo modulo. Per riutilizzare la stessa funzione nel contesto di un sotto-modulo, si crea un Vec temporaneo con il nuovo modulo in posizione [0]. Le chiamate ricorsive a walk_cst inseriranno i componenti trovati in new_modules[0], che è il modulo appena creato.

4.4 Gestione Speciale delle Funzioni

Riga 48-56

crate::heuristics::ParsedItem::Component(crate::ir::Component::Function(ff)) => {
    // 1. Inserisce la funzione nel modulo corrente
    modules[0].free_functions.push(ff);

    // 2. Attraversa i figli "body" per cercare componenti annidati
    let mut cursor = node.walk();
    for child in node.children(&mut cursor) {
        if child.kind().contains("body") || child.kind().contains("block") {
            walk_cst(child, source, modules);
        }
    }
}

Quando viene riconosciuta una funzione, il nodo non viene completamente ignorato come per gli altri componenti. Il sistema continua a cercare componenti nel corpo della funzione — ma solo nei nodi di tipo "body" o "block". Questo gestisce il caso di struct o classi definite dentro una funzione (possibile in alcuni linguaggi).

Attenzione: In questa seconda discesa, i componenti trovati vengono inseriti nel modulo corrente (modules), non in un modulo separato. Questo significa che una struct definita dentro una funzione viene trattata come una struct del modulo — non c'è concetto di "scope locale" per le definizioni all'interno dei corpi delle funzioni.

4.5 Il return Anti-Duplicazione

Riga 60

Dopo aver processato un componente riconosciuto (tranne le eccezioni sopra), la funzione esegue return — non scende nei figli del nodo. Questo è fondamentale per evitare duplicazioni: senza il return, i metodi di una struct verrebbero estratti sia come metodi della struct (dal parser della struct) sia come funzioni libere (da una chiamata ricorsiva separata).

5. Il Dispatcher Euristico: dispatch_node

Riferimento: heuristics/mod.rs:15-32

Il dispatcher è il cervello decisionale. Per ogni nodo del CST, prova a classificarlo in ordine di priorità fisso:

pub fn dispatch_node(node: Node, source: &str) -> Option<ParsedItem> {
    // 1. Import (priorità massima)
    if let Some(import) = parsers::try_parse_import(node, source) {
        return Some(ParsedItem::Import(import));
    }
    // 2. Module
    if let Some(m) = parsers::try_parse_module_node(node, source) {
        return Some(ParsedItem::Component(Component::Module(m)));
    }
    // 3. Structured Type (struct, class, interface, trait)
    if let Some(st) = parsers::try_parse_structured_type(node, source) {
        return Some(ParsedItem::Component(Component::StructuredType(st)));
    }
    // 4. Function
    if let Some(ff) = parsers::try_parse_function(node, source) {
        return Some(ParsedItem::Component(Component::Function(ff)));
    }
    // 5. Impl Block (priorità minima)
    if let Some(implb) = parsers::try_parse_impl_block(node, source) {
        return Some(ParsedItem::ImplBlock(implb));
    }
    None  // Nodo non riconosciuto
}
L'ordine conta: Le funzioni try_parse_* vengono chiamate in sequenza e il primo match vince (early return). L'ordine è scelto strategicamente:
  • Import prima di tutto: Le dichiarazioni di import hanno una grammatica molto distinta e non ambigua.
  • Module prima di Struct: Un mod_item in Rust potrebbe contenere la stringa "struct" nei figli — il check del modulo deve avvenire prima.
  • Struct prima di Function: In alcuni linguaggi, una classe contiene metodi — ma il nodo classe deve essere catturato intero, non frammentato in funzioni singole.
  • Impl Block per ultimo: In Rust, impl_item contiene "impl" che potrebbe generare falsi positivi con altri pattern.

Ogni funzione try_parse_* opera in due fasi: prima chiama un classificatore (booleano) per verificare il tipo, poi chiama gli estrattori per popolare la struttura IR.

6. Livello 1 — Classificatori

Riferimento: heuristics/classifiers.rs

I classificatori sono funzioni booleane pure che rispondono alla domanda: "Questo nodo CST è un [tipo di componente]?". Usano un approccio euristico basato su stringhe per essere indipendenti dal linguaggio.

6.1 is_module

pub fn is_module(node: Node) -> bool {
    if !node.is_named() { return false; }
    let kind = node.kind();
    kind.contains("mod_item") || kind.contains("module") || kind.contains("namespace")
}

Riconosce moduli, namespaces e package. Copre:

LinguaggioNode KindMatch
Rustmod_item✓ contiene "mod_item"
Pythonmodule✓ contiene "module"
C++namespace_definition✓ contiene "namespace"

6.2 is_structured_type

pub fn is_structured_type(node: Node) -> bool {
    if !node.is_named() { return false; }
    let kind = node.kind();
    (kind.contains("struct") || kind.contains("class") || kind.contains("interface")
     || kind.contains("trait") || kind.contains("enum") || kind.contains("union"))
    && !kind.contains("bound") && !kind.contains("clause") && !kind.contains("list")
    && !kind.contains("expression") && !kind.contains("argument") && !kind.contains("call")
    && !kind.contains("identifier") && !kind.contains("reference") && !kind.contains("body")
    && !kind.contains("mod") && !kind.contains("variant")
    && !kind.contains("super") && !kind.contains("base") && !kind.contains("constructor")
}

La logica è un pattern positivo (deve contenere "struct", "class", ecc.) con esclusioni negative per evitare falsi positivi. Ad esempio:

  • "struct_item" → ✓ match (contiene "struct")
  • "struct_expression" → ✗ escluso (contiene "expression") — è un'istanziazione, non una definizione
  • "class_body" → ✗ escluso (contiene "body") — è il corpo della classe, non la dichiarazione
  • "constructor_declaration" → ✗ escluso (contiene "constructor") — pur contenendo la parola "struct" (constructor), viene escluso per evitare falsi positivi in Java/C++.

6.3 is_function

pub fn is_function(node: Node) -> bool {
    if !node.is_named() { return false; }
    let kind = node.kind();
    kind.contains("function") || kind.contains("method")
     || kind.contains("fn_item") || kind.contains("def") || kind.contains("func")
}

Copre la maggior parte delle definizioni di funzione/metodo attraverso i linguaggi:

LinguaggioNode KindMatch
Rustfunction_item✓ "function"
Javamethod_declaration✓ "method"
Pythonfunction_definition✓ "function" e "def"
C/C++function_definition✓ "function"

6.4 is_impl_block e is_import

pub fn is_impl_block(node: Node) -> bool {
    if !node.is_named() { return false; }
    node.kind().contains("impl")
}

pub fn is_import(node: Node) -> bool {
    if !node.is_named() { return false; }
    matches!(node.kind(),
        "use_declaration" | "import_declaration" | "import_statement"
        | "import_from_statement" | "preproc_include"
    )
}

is_import è l'unico classificatore che usa matches! (confronto esatto) invece di contains. Questo perché i nomi dei nodi di import sono molto specifici e un matching parziale causerebbe troppi falsi positivi.

7. Livello 2 — Parser

Riferimento: heuristics/parsers.rs

Ogni funzione try_parse_* prima invoca il classificatore corrispondente, poi usa gli estrattori per popolare la struttura IR.

7.1 try_parse_module_node

pub fn try_parse_module_node(node: Node, source: &str) -> Option<Module> {
    if !is_module(node) { return None; }

    let name = extract_identifier(node, source)
        .unwrap_or_else(|| "unnamed_module".to_string());

    Some(Module {
        name: vec![name],
        imports: vec![],         // ← Vuoto: gli import verranno aggiunti da walk_cst
        sub_modules: vec![],     // ← Vuoto: i sotto-moduli verranno aggiunti da walk_cst
        structured_types: vec![],
        free_functions: vec![],
        impl_blocks: vec![],
    })
}
Modulo "vuoto": Il parser crea un modulo con solo il nome — tutti gli altri campi sono vuoti. Sarà walk_cst (Sezione 4.3) a ri-attraversare i figli del nodo CST e a popolare il modulo con i componenti trovati al suo interno.

7.2 try_parse_structured_type

pub fn try_parse_structured_type(node: Node, source: &str) -> Option<StructuredType> {
    if !is_structured_type(node) { return None; }

    let kind_text = node.kind();
    let text = node_text(node, source);
    let name = extract_qualified_name(node, source)
        .unwrap_or_else(|| vec!["unnamed_type".to_string()]);

    let fields = extract_fields(node, source);           // Campi
    let methods = extract_methods(node, source);         // Metodi
    let super_types = extract_super_types(node, source); // Eredità
    let nested_types = extract_nested_types(node, source); // Tipi annidati

    Some(StructuredType {
        name,
        kind: determine_structured_kind(kind_text, &text),
        fields, methods, super_types, nested_types,
    })
}

A differenza dei moduli, i tipi strutturati vengono popolati completamente dal parser — campi, metodi, super-tipi e tipi annidati sono tutti estratti in questa fase. Non c'è bisogno di ri-attraversare il CST da walk_cst.

7.3 try_parse_function

pub fn try_parse_function(node: Node, source: &str) -> Option<Function> {
    if !is_function(node) { return None; }

    let name = extract_identifier(node, source)
        .unwrap_or_else(|| "unnamed_function".to_string());
    let parameters = extract_parameters(node, source);
    let return_type = extract_return_type(node, source);

    // Estrazione strutturata del body
    let body = if let Some(body_node) = node.child_by_field_name("body") {
        Some(extract_block(body_node, source))
    } else {
        None
    };

    Some(Function {
        name: vec![name],
        signature: Signature { parameters, return_type },
        body,
    })
}

Oltre a nome, parametri e tipo di ritorno, il parser estrae il corpo della funzione come un Block strutturato tramite extract_block. Il Block risultante contiene dichiarazioni locali, dipendenze comportamentali (chiamate e istanziazioni) e sotto-blocchi annidati (vedi Sezione 10). Se la funzione non ha un body (es. dichiarazioni in header), il campo è None.

7.4 try_parse_impl_block

pub fn try_parse_impl_block(node: Node, source: &str) -> Option<ImplBlock> {
    if !is_impl_block(node) { return None; }

    let name = extract_qualified_name(node, source)
        .unwrap_or_else(|| vec!["unnamed_impl".to_string()]);
    let methods = extract_methods(node, source);
    let impl_for = extract_impl_for(node, source);
    let implements_trait = extract_implements_trait(node, source);
    let nested_types = extract_nested_types(node, source);

    Some(ImplBlock { name, methods, impl_for, implements_trait, nested_types })
}

7.5 try_parse_import

pub fn try_parse_import(node: Node, source: &str) -> Option<Import> {
    if !is_import(node) { return None; }

    let text = node_text(node, source);

    // 1. Determina se è un wildcard import
    let is_wildcard = text.contains('*') || text.contains(".*") || text.contains("::*");

    // 2. Cerca un alias (es. "as Db")
    let mut alias = None;
    if let Some(as_pos) = text.find(" as ") {
        let after_as = text[as_pos + 4..].trim();
        let alias_part: String = after_as.chars()
            .take_while(|c| c.is_alphanumeric() || *c == '_').collect();
        if !alias_part.is_empty() { alias = Some(alias_part); }
    }

    // 3. Estrai il percorso dell'import
    let path = /* ... vari tentativi con named fields e fallback ... */;

    if path.is_empty() { return None; }
    Some(Import { path, alias, is_wildcard })
}

Il parsing degli import combina approcci strutturali (named fields del CST) con fallback testuali (text.find(" as ")) per gestire variazioni tra linguaggi diversi.

8. Livello 3 — Estrattori

Riferimenti: heuristics/text_parsing.rs, heuristics/structural_extraction.rs

Gli estrattori sono le funzioni di più basso livello. Interagiscono direttamente con i nodi CST di Tree-sitter per estrarre dati specifici. Questo livello è stato recentemente fattorizzato in più file per massimizzare la coesione del codice.

8.1 node_text — Estrazione del testo grezzo

pub fn node_text(node: Node, source: &str) -> String {
    node.utf8_text(source.as_bytes()).unwrap_or("").to_string()
}

Funzione fondamentale: estrae il testo del codice sorgente corrispondente a un nodo CST. Tree-sitter memorizza solo le posizioni (byte offset) dei nodi — il testo viene letto dalla stringa sorgente originale.

8.2 split_qualified_name — Parsing dei nomi qualificati

pub fn split_qualified_name(text: &str) -> QualifiedName {
    text.split(&[':', '.', ' '][..])
        .filter(|s| !s.trim().is_empty())
        .map(|s| s.trim().to_string())
        .collect()
}

Divide nomi qualificati come "std::vec::Vec", "java.util.List" e "A B" in vettori: ["std", "vec", "Vec"]. I separatori supportati sono :, . e spazio.

8.3 extract_identifier — Estrazione del nome semplice

pub fn extract_identifier(node: Node, source: &str) -> Option<String> {
    // Tentativo 1: named fields comuni
    if let Some(n) = node.child_by_field_name("name")
        .or_else(|| node.child_by_field_name("type_identifier"))
        .or_else(|| node.child_by_field_name("identifier"))
    { ... }

    // Tentativo 2: campo "declarator" (tipico di C/C++)
    if let Some(decl) = node.child_by_field_name("declarator") { ... }

    None
}

Cerca il nome di un componente usando una catena di named fields progressivamente meno specifici. Il fallback al declarator gestisce le dichiarazioni C/C++ dove il nome è annidato dentro il dichiaratore.

8.4 extract_qualified_name — Estrazione del nome completo

pub fn extract_qualified_name(node: Node, source: &str) -> Option<QualifiedName> {
    // Tentativo 1: named fields → split_qualified_name
    if let Some(n) = node.child_by_field_name("name")... {
        return Some(split_qualified_name(&node_text(n, source)));
    }

    // Tentativo 2: raccogli tutti gli identifier figli
    let mut parts = vec![];
    for child in node.children(...) {
        if matches!(child.kind(), "identifier" | "type_identifier" | "name") {
            parts.push(node_text(child, source));
        }
    }
    if !parts.is_empty() { Some(parts) } else { None }
}

A differenza di extract_identifier, questa funzione supporta nomi multi-parte (es. A::B::C). Il fallback manuale raccoglie tutti i figli "identifier" per ricostruire il nome qualificato.

8.5 extract_list_of — Estrattore generico per liste

pub fn extract_list_of<T, F>(node: Node, source: &str, parser: F) -> Vec<T>
where F: Fn(Node, &str) -> Option<T> + Copy
{
    let mut items = vec![];
    for child in node.children(...) {
        if let Some(item) = parser(child, source) {
            items.push(item);
        } else if !crate::heuristics::classifiers::is_function(child) && (
               child.kind().contains("body") || child.kind().contains("list")
               || child.kind().contains("block") || child.kind().contains("declaration")) {
            items.extend(extract_list_of(child, source, parser));  // Ricorsione!
        }
    }
    items
}

Funzione generica parametrizzata: riceve una funzione parser e la applica a tutti i figli del nodo. Se un figlio non viene riconosciuto dal parser ma è un nodo "contenitore" (body, list, block, declaration), scende ricorsivamente al suo interno. Il controllo !is_function(child) è fondamentale: previene che l'estrattore scenda all'interno del corpo dei metodi per cercare campi, evitando di estrarre erroneamente variabili locali come campi della classe.

Viene usata per estrarre:

  • extract_fields(node, source) → usa un parser inline per field_declaration
  • extract_methods(node, source) → usa try_parse_function
  • extract_nested_types(node, source) → usa try_parse_structured_type

8.6 extract_parameters — Parametri di funzione

pub fn extract_parameters(node: Node, source: &str) -> Vec<Parameter> {
    if let Some(params_node) = node.child_by_field_name("parameters") {
        for p in params_node.children(...) {
            if p.kind().contains("parameter") {
                let name = extract_identifier(p, source);
                let ty = extract_type_ref(p, source);
                let is_variadic = text.contains("...") || text.contains("*args");
                params.push(Parameter { name, ty, is_variadic });
            }
        }
    }
}

Cerca il nodo "parameters" come named field, poi itera sui figli di tipo "parameter" per estrarre nome, tipo e flag variadico.

8.7 extract_return_type — Tipo di ritorno

pub fn extract_return_type(node: Node, source: &str) -> TypeRef {
    // Tentativo 1: named fields "return_type" o "type"
    if let Some(type_node) = node.child_by_field_name("return_type")
        .or_else(|| node.child_by_field_name("type")) { ... }

    // Tentativo 2: fallback testuale — cerca "->" nel testo del nodo
    if let Some(arrow_pos) = text.find("->") { ... }

    TypeRef::Failed(vec![])  // Nessun tipo di ritorno trovato
}

8.8 extract_super_types — Ereditarietà e implementazione

Questa funzione è la più complessa degli estrattori. Cerca tipi padre/interfacce in una serie di named fields:

  • "super_type", "extends", "implements" — Java
  • "superclass", "superclasses" — Python
  • "interfaces" — Java
  • Nodi figli di tipo "base_class_clause" — C++

Per ciascun nodo trovato, attraversa i figli cercando type_identifier, identifier, scoped_type_identifier e liste di tipi.

8.9 extract_implements_trait — Trait implementato da un impl block

pub fn extract_implements_trait(node: Node, source: &str) -> Option<TypeRef> {
    let text = node_text(node, source);
    if let Some(for_pos) = text.find("for ") {
        let before_for = text[..for_pos].trim();
        if before_for.contains("impl") && !before_for.ends_with("impl") {
            // Es: "impl Trait for Type" → prima di "for" c'è "impl Trait"
            // Estrae "Trait" come nome
            ...
        }
    }
    None
}

Usa un approccio puramente testuale: cerca la keyword "for " nel testo del nodo e analizza ciò che appare tra "impl" e "for". Se c'è qualcosa (il nome di un trait), lo restituisce come TypeRef::Unresolved.

9. Estrazione dei Tipi: extract_type_ref

Riferimento: heuristics/type_extraction.rs

Questa funzione è usata ovunque serva estrarre un riferimento a un tipo (campi, parametri, tipo di ritorno, ecc.). Opera con una cascata di tentativi sempre più generici:

Step 0 — Nodi diretti di tipo/identificatore

if matches!(kind, "field_access" | "scoped_identifier" | "qualified_identifier"
                 | "identifier" | "type_identifier" | "attribute") {
    let text = node_text(node, source);
    if !text.is_empty() {
        return TypeRef::Unresolved(split_qualified_name(&text));
    }
}

Se il nodo stesso è già un identificatore o un accesso qualificato, estrae direttamente il testo e lo splitta in un nome qualificato.

Step 1 — Named fields del CST

if let Some(type_node) = node.child_by_field_name("type")
    .or_else(|| node.child_by_field_name("return_type"))
    .or_else(|| node.child_by_field_name("field_type"))
    .or_else(|| node.child_by_field_name("value_type"))
{
    return TypeRef::Unresolved(split_qualified_name(&node_text(type_node, source)));
}

Cerca un figlio con nome semantico relativo al tipo. Questo è il percorso più affidabile — usa i named fields di Tree-sitter che sono specifici per grammatica.

Step 2 — Ricerca dei figli identificatore

for child in node.children(...) {
    if matches!(child_kind, "type_identifier" | "primitive_type" | "identifier" | "type") {
        let text = node_text(child, source);
        if !text.is_empty() && !text.contains(" ") {
            return TypeRef::Unresolved(split_qualified_name(&text));
        }
    }
}

Se i named fields non hanno prodotto risultati, scorre tutti i figli del nodo cercando nodi di tipo identificatore. Il check !text.contains(" ") evita di catturare espressioni complesse scambiate per nomi di tipo.

Step 3 — Fallback testuale puro

let text = node_text(node, source);
// Cerca dopo ":"  (es. "x: String")
if let Some(colon_pos) = text.find(':') { ... }
// Cerca dopo "->" (es. "-> i32")
if let Some(arrow_pos) = text.find("->") { ... }

L'ultimo tentativo è completamente testuale: cerca i caratteri : o -> nel testo del nodo e prende tutto ciò che segue. Questo gestisce i casi in cui Tree-sitter non espone named fields per il tipo.

Fallimento

TypeRef::Failed(vec![])

Se nessun tentativo riesce, viene restituito un TypeRef::Failed con nome vuoto.

10. Estrazione Strutturata del Body: extract_block

Riferimento: heuristics/body_extraction.rs

L'analisi del corpo di una funzione è gestita dalla funzione extract_block, che sostituisce la precedente traverse_for_body_deps. Il nuovo approccio produce un Block strutturato che modella la gerarchia degli scope del codice, separando dichiarazioni locali, dipendenze comportamentali e blocchi annidati. Durante la visita, infer_variable_type compensa le variabili omesse tipizzando dal lato destro dell'espressione.

10.1 extract_block — Estrazione strutturata

pub fn extract_block(node: Node, source: &str) -> Block {
    let mut declarations = vec![];
    let mut calls = vec![];
    let mut instantiates = vec![];
    let mut accesses = vec![];
    let mut sub_blocks = vec![];
    let mut cursor = node.walk();

    for child in node.children(&mut cursor) {
        let kind = child.kind();

        // 1. Dichiarazioni di variabili locali
        if matches!(kind, "field_declaration" | "property_declaration" | "field"
            | "member_declaration" | "variable_declarator" | "attribute"
            | "local_variable_declaration" | "lexical_declaration"
            | "variable_declaration" | "let_declaration")
        {
            if let Some(name) = extract_identifier(child, source) {
                let ty = extract_type_ref(child, source);
                declarations.push(Field { name, ty });
            }
        }
        // 2. Blocchi annidati (if/while/scope anonimi)
        else if kind.contains("body") || kind.contains("block")
             || kind == "compound_statement"
        {
            sub_blocks.push(extract_block(child, source));
        }
        // 3. Dipendenze comportamentali (nodi non-blocco)
        else {
            let mut inner_calls = vec![];
            let mut inner_inst = vec![];
            let mut inner_acc = vec![];
            find_behavioral_deps(child, source, &mut inner_calls, &mut inner_inst, &mut inner_acc);
            calls.extend(inner_calls);
            instantiates.extend(inner_inst);
            accesses.extend(inner_acc);
        }
    }

    Block { declarations, calls, instantiates, accesses, sub_blocks }
}

La funzione opera sui figli diretti del nodo body, classificandoli in tre categorie:

Categoria 1 — Dichiarazioni di variabili locali

I nodi che rappresentano dichiarazioni di variabili (let_declaration, local_variable_declaration, lexical_declaration, ecc.) vengono estratti come Field { name, ty } e aggiunti a declarations. Questo cattura le variabili locali del blocco con il loro tipo (quando disponibile).

LinguaggioEsempioNode Kind
Rustlet x: i32 = 5;let_declaration
JavaString s = "hello";local_variable_declaration
JavaScript/TSlet x = 10;lexical_declaration
C/C++int count = 0;variable_declaration
Pythonself.x = 5attribute

Categoria 2 — Blocchi annidati (ricorsione)

Se un figlio è un blocco (il suo kind() contiene "body" o "block", oppure è un "compound_statement"), viene processato ricorsivamente con extract_block e il risultato viene aggiunto a sub_blocks. Questo crea la gerarchia di Block annidati.

// Esempio: un if con un body annidato
fn esempio() {
    let x = 5;               // ← declarations del Block principale
    if x > 0 {               // ← il body dell'if diventa un sub_block
        let y = 10;           //   ← declarations del sub_block
        calcola(y);           //   ← calls del sub_block
    }
    stampa(x);                // ← calls del Block principale
}

Categoria 3 — Dipendenze comportamentali

Tutti gli altri nodi (espressioni, statement non-blocco, ecc.) vengono passati a find_behavioral_deps per cercare chiamate e istanziazioni. Questa funzione cerca ricorsivamente nel sottoalbero ma salta i blocchi annidati per evitare il double-counting.

10.2 find_behavioral_deps — Ricerca dipendenze senza double-counting

La funzione find_behavioral_deps cerca ricorsivamente chiamate a funzione e istanziazioni nel sottoalbero di un nodo, ma si ferma quando incontra un nodo di tipo blocco (che sarà processato separatamente da extract_block).

Istanziazioni (instantiates)

// Java/C++: new MyClass()
if matches!(kind, "object_creation_expression" | "new_expression") {
    if let Some(t_node) = node.child_by_field_name("type") {
        instantiates.push(extract_type_ref(t_node, source));
    }
}
// Rust: MyStruct { ... }
else if kind == "struct_expression" {
    if let Some(name_node) = node.child_by_field_name("name") {
        instantiates.push(extract_type_ref(name_node, source));
    }
}

Chiamate a funzione (calls)

// Chiamate generiche: func(), obj.method(), Module::func()
if matches!(kind, "call_expression" | "call") {
    if let Some(f) = node.child_by_field_name("function") {
        // Scoped: Module::func() → estrae "Module"
        if matches!(f_kind, "qualified_identifier" | "scoped_identifier") {
            calls.push(extract_type_ref(scope, source));
        }
        // Method: obj.method() → estrae "obj"
        else if matches!(f_kind, "field_expression" | "attribute") {
            calls.push(extract_type_ref(obj, source));
        }
        // Simple: func() → estrae "func"
        else if matches!(f_kind, "identifier" | "type_identifier") {
            calls.push(extract_type_ref(f, source));
        }
    }
}
// Java method invocations: obj.method()
else if kind == "method_invocation" {
    calls.push(extract_type_ref(obj_or_name, source));
}

Per le chiamate, la logica varia in base alla forma sintattica:

PatternTipo CSTCosa viene estratto
Module::func()scoped_identifierLo "scope" (es. Module)
obj.method()field_expressionL'"object" (es. obj)
func()identifierL'identificatore (es. func)
obj.method() (Java)method_invocationL'"object" o il "name"

Accessi a stato (accesses)

// Accesso a campi o costanti: obj.field, Class.CONSTANT
if matches!(kind, "field_access" | "member_expression" | "scoped_identifier") {
    // Si estrae l'oggetto o la classe su cui avviene l'accesso
    if let Some(obj) = node.child_by_field_name("object").or_else(|| node.child_by_field_name("path")) {
        accesses.push(extract_type_ref(obj, source));
    }
}

Questo permette di intercettare l'accoppiamento verso campi statici, variabili di istanza e costanti (come gli Enum) catturando il prefisso dell'espressione.

Differenza chiave rispetto al vecchio traverse_for_body_deps: La vecchia funzione attraversava ricorsivamente tutti i figli senza distinzione, raccogliendo chiamate e istanziazioni in liste piatte. Il nuovo approccio con extract_block + find_behavioral_deps separa le dipendenze per livello di scope: find_behavioral_deps salta i nodi blocco (che vengono gestiti da extract_block come sub_blocks), evitando così il double-counting.

11. Esempio Completo End-to-End

Seguiamo l'intero processo per il seguente codice Rust:

use external::db::Database as Db;

mod core {
    struct Veicolo {
        id: String,
    }
    struct Auto {
        base: Veicolo,
    }
    fn calcola() -> Auto {
        let v = Auto { base: Veicolo { id: String::new() } };
        v
    }
}

struct User {
    name: String,
}

Passo 1 — Parsing Tree-sitter

generic_extract(rust(), source) crea il parser Rust e genera il CST. Il nodo radice è source_file.

Passo 2 — Prima chiamata walk_cst(source_file, ...)

Il dispatcher viene invocato su source_file → restituisce None (non è un componente riconosciuto). Quindi walk_cst scende nei figli del nodo radice. I figli diretti sono:

  1. use_declaration — use external::db::Database as Db
  2. mod_item — mod core { ... }
  3. struct_item — struct User { ... }

Passo 3 — Nodo use_declaration

  1. dispatch_node → chiama try_parse_import → is_import restituisce true (matches "use_declaration").
  2. Parsing dell'import:
    • is_wildcard: il testo non contiene * → false
    • alias: trova " as " nel testo → estrae "Db"
    • path: cerca named field "argument" → trova il nodo scoped_identifier → testo "external::db::Database" → split → ["external", "db", "Database"]
  3. Risultato: Import { path: ["external", "db", "Database"], alias: Some("Db"), is_wildcard: false }
  4. Inserimento: modules è vuoto → crea modulo "root" → inserisce l'import in modules[0].imports.

Passo 4 — Nodo mod_item (mod core)

  1. dispatch_node → try_parse_import fallisce → try_parse_module_node → is_module restituisce true (kind "mod_item" contiene "mod_item").
  2. Parsing: extract_identifier → named field "name" → "core". Crea Module { name: ["core"], ... } (tutto vuoto).
  3. walk_cst crea new_modules = [Module("core")] e ri-attraversa i figli del nodo mod_item.

Passo 4a — Figlio: struct_item (struct Veicolo)

  1. dispatch_node → try_parse_structured_type → is_structured_type true (contiene "struct").
  2. Parsing:
    • name → ["Veicolo"]
    • kind → StructuredTypeKind::Struct
    • fields → extract_fields trova field_declaration "id: String" → [Field { name: "id", ty: Unresolved(["String"]) }]
    • methods → [], super_types → [], nested_types → []
  3. Inserimento: In new_modules[0].structured_types (cioè nel modulo "core").
  4. return — non scende nei figli della struct.

Passo 4b — Figlio: struct_item (struct Auto)

  1. Stessa logica. fields → [Field { name: "base", ty: Unresolved(["Veicolo"]) }]
  2. Inserito in new_modules[0].structured_types.

Passo 4c — Figlio: function_item (fn calcola)

  1. dispatch_node → try_parse_function → is_function true.
  2. Parsing:
    • name → "calcola"
    • parameters → []
    • return_type → named field "return_type" → testo "Auto" → Unresolved(["Auto"])
    • body → extract_block sul nodo body produce:
      • declarations: [Field { name: "v", ty: Unresolved(["Auto"]) }] — la variabile let v
      • instantiates: [Unresolved(["Auto"]), Unresolved(["Veicolo"])] — le struct_expression
      • calls: [Unresolved(["String"])] — da String::new()
      • sub_blocks: [] — nessun blocco annidato
  3. Inserito in new_modules[0].free_functions.

Completamento del Passo 4: il modulo "core" è ora popolato. Viene inserito in modules[0].sub_modules → il modulo "root" ora contiene il sotto-modulo "core".

Passo 5 — Nodo struct_item (struct User)

  1. dispatch_node → try_parse_structured_type → true.
  2. name → ["User"], fields → [Field { name: "name", ty: Unresolved(["String"]) }].
  3. Inserito in modules[0].structured_types (il modulo "root").

Risultato Finale dell'IR

L'output di generic_extract è:

Module "root" ├── imports: [ external::db::Database as Db ] ├── structured_types: [ User { name: String } ] ├── free_functions: [ ] ├── impl_blocks: [ ] └── sub_modules: └── Module "core" ├── imports: [ ] ├── structured_types: │ ├── Veicolo { id: Unresolved(String) } │ └── Auto { base: Unresolved(Veicolo) } ├── free_functions: │ └── calcola() → Unresolved(Auto) │ body: Block │ ├── declarations: [ v: Unresolved(Auto) ] │ ├── calls: [ Unresolved(String) ] │ ├── instantiates: [ Unresolved(Auto), Unresolved(Veicolo) ] │ └── sub_blocks: [ ] ├── impl_blocks: [ ] └── sub_modules: [ ]

Questa struttura verrà poi passata alla Fase 2 (Name Resolution) che trasformerà tutti i TypeRef::Unresolved in Resolved, External o Failed.

12. Orchestrazione Multi-File (Workspace Aggregation) e Configurazione Strategie

Riferimento: src/main.rs (funzione analyze_directory)

Mentre generic_extract (e la Fase 1 vera e propria) opera sul singolo file sorgente, l'analizzatore architetturale è progettato per funzionare su interi progetti multi-file. Questo avviene attraverso una fase di orchestrazione pre-risoluzione che unifica i moduli.

Tutti i moduli estratti singolarmente da tutti i file vengono raggruppati in un unico, gigantesco Vec<Module> globale (il "Workspace"). Solo dopo che tutti i file sono stati estratti e unificati, viene invocato il Query Engine (Fase 2) sull'intero workspace. Questo elimina la barriera del singolo file: le dipendenze esterne al file locale diventeranno risolte magicamente perché il resolver opera su tutto il progetto contemporaneamente.

12.1 Strategie Architetturali Basate su Configurazione

L'architettura supporta un sistema di Configurazione Globale (AnalyzerConfig) che mappa il comportamento dell'estrazione e della risoluzione a seconda del linguaggio e delle strategie selezionate (ad esempio, tramite un file JSON passato via CLI o tramite default pre-impostati).

Una delle strategie architetturali più impattanti applicate durante la fase di estrazione (precisamente in parse_source) è la gestione del namespace, determinata dalla ModuleStrategy.

DirectoryBased Namespacing: Linguaggi come Python e Rust utilizzano spesso i percorsi delle cartelle e dei file come base implicita del loro namespace (es: src/core/utils.py diventa implicitamente il modulo src::core::utils). Se il LanguageConfig associato al linguaggio in uso abilita la ModuleStrategy::DirectoryBased, la funzione parse_source applica una logica di "wrapping" automatica:

1. Prende i componenti top-level estratti originariamente dentro un modulo base root.
2. Determina i segmenti del percorso del file rispetto alla directory di esecuzione.
3. Costruisce una gerarchia di moduli IR nidificati, inserendo i componenti analizzati all'interno dell'ultimo nodo della gerarchia (che prende il nome del file senza estensione).
4. Infine, incapsula il tutto sotto al generico nodo root del progetto, permettendo al Resolver Globale di navigare agevolmente tra i file del progetto partendo dalla medesima struttura logica.

Questo meccanismo permette di astrarre i dettagli fisici del filesystem mantenendo coerente il lexical scoping a livello di Workspace Globale. Nel momento in cui i moduli unificati passano alla Fase 2 (Name Resolution), i resolver navigheranno tra i moduli indipendentemente dal fatto che provenissero o meno dallo stesso file, rendendo il Query Engine interamente agnostico.
