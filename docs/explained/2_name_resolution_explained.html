1. Panoramica e Obiettivo

La Name Resolution (Risoluzione dei Riferimenti) è il cuore logico dell'analizzatore architetturale. È la fase che trasforma nomi grezzi e ambigui — estratti dal parser nella Fase 1 — in identificatori univoci e globalmente validi. Senza questa fase, l'analizzatore non saprebbe se Veicolo scritto in un file si riferisce alla struct root::core::Veicolo, a un tipo esterno importato, o a un tipo inesistente.

Perché è il cuore del sistema? Perché l'intero grafo delle dipendenze (Fase 3) si basa sui risultati della risoluzione. Se un tipo viene marcato erroneamente come Failed, scompare un arco dal grafo. Se viene marcato come External invece di Resolved, il grafo mostra una dipendenza verso una libreria esterna inesistente. La qualità dell'analisi architetturale dipende interamente dalla correttezza della risoluzione locale e globale.

1.1 Il Problema Fondamentale

Quando il parser estrae dall'AST un riferimento come Veicolo, non sa quale Veicolo sia. Potrebbe essere:

  • La struct Veicolo definita nello stesso modulo → Resolved
  • Un tipo importato da una libreria esterna → External
  • Un tipo primitivo del linguaggio come String → Primitive
  • Un tipo che non esiste da nessuna parte → Failed

Il resolver deve operare questa classificazione per ogni singolo TypeRef nell'IR — nei campi delle struct, nei parametri delle funzioni, nei tipi di ritorno, nelle dichiarazioni locali, nelle chiamate e nelle istanziazioni.

1.2 La Macchina a Stati di TypeRef

Ogni riferimento di tipo attraversa una sequenza di stati definiti nell'enum TypeRef (model/queries.rs):

StatoSignificatoChi lo produceEsempio
Unresolved(path) Nome grezzo estratto dal parser. È il punto di partenza: il tipo è un semplice token testuale senza contesto semantico. Fase 1 (Estrazione) ["Veicolo"]
ResolutionQuery(Query) Stato intermedio prodotto dalla sostituzione lessicale. Le variabili locali sono state espanse in query algebriche, ma il percorso assoluto non è ancora stato determinato. Fase 2a (Builder) Extract(Find("T"), "f")
Resolved(path) Nome risolto con successo. Il percorso è assoluto e punta a un componente presente nel progetto analizzato. Fase 2b (Executor) ["root", "core", "Veicolo"]
External(path) Nome riconosciuto tramite un import, ma il componente non è presente nell'IR locale — è una dipendenza esterna. Fase 2b (Executor) ["external", "db", "Database"]
Primitive(type) Tipo primitivo del linguaggio corrente, riconosciuto dal PrimitiveRegistry data-driven. Fase 2b (Executor) Primitive(Other("String"))
Failed(path) Tutti i tentativi di risoluzione sono falliti. Il nome rimane irrisolto — nel grafo non verrà generato alcun arco. Fase 2b (Executor) ["UnknownType"]

1.3 Posizione nella Pipeline (Workspace Aggregation)

1. Estrazione CST→IR (Per File) → 1.5 Workspace Aggregation → 2a. Query Building → 2b. Query Execution → 3. Dependency Graph

Riferimento: src/resolver/mod.rs:10-21, e src/main.rs:55-66

Un aspetto architetturale cruciale è la Workspace Aggregation: la Fase 2 (Name Resolution) non viene eseguita su un singolo file alla volta. Nel loop principale in main.rs, i Vec<Module> estratti singolarmente da tutti i file del progetto vengono "fusi" (tramite append) in un unico gigantesco Vec<Module> globale, chiamato Workspace.

Solo dopo aver raccolto tutto il progetto, viene invocato il resolver globale:

pub fn resolve_type_refs(modules: Vec<Module>, primitives: &PrimitiveRegistry) -> Vec<Module> {
    // Fase 2a: Sostituzione lessicale — produce ResolutionQuery
    let modules_with_queries = builder::build_queries(modules);
    // Fase 2b: Navigazione globale — produce Resolved/External/Failed/Primitive
    let resolved_modules = executor::execute_queries(modules_with_queries, primitives);
    resolved_modules
}

Questo approccio "Tutto-in-Uno" elimina i problemi di ordine di compilazione e consente alla risoluzione di attraversare file diversi come se fossero un unico grande documento sorgente.

2. Architettura: dal Monofase al Query Engine Bifase

2.1 Evoluzione Storica

L'architettura di risoluzione ha attraversato tre iterazioni fondamentali:

VersioneApproccioStruttura dati principaleProblema fondamentale
v1 Arena + ScopeTree statico ScopeTree { arena: Vec<ScopeNode> } Il current_scope non veniva mai aggiornato — tutto partiva da ROOT
v2 SymbolStack monofase SymbolStack { frames: Vec<StackFrame> } con String → QualifiedName Forward references impossibili; niente catene di chiamate; primitivi marcati come Failed
v3 (attuale) Query Engine bifase SymbolStack con String → Query + Scope Tree con RegistryEntry —

2.2 Perché il Modello Monofase (v2) Non Era Sufficiente

Nella v2, la risoluzione avveniva in un singolo pass: durante l'attraversamento dell'IR, ogni Unresolved veniva immediatamente risolto. Questo causava tre problemi strutturali:

Problema 1: Forward References

Se il tipo Auto è dichiarato dopo calcola() nel codice sorgente, quando il resolver incontra -> Auto nella firma della funzione, il tipo non è ancora stato registrato nello stack. L'ordine di dichiarazione nel codice sorgente influenza il risultato della risoluzione — violazione del principio di declaration-order independence.

Problema 2: Catene di Chiamate

L'espressione a.f().g() richiede di conoscere il tipo di ritorno di f() per risolvere g(). Nella v2, lo stack mappava String → QualifiedName — un percorso assoluto, non un'espressione risolvibile. Non c'era modo di esprimere "chiama f, prendi il tipo di ritorno, poi cerca g su quel tipo".

Problema 3: Mixing di Responsabilità

Il singolo pass mescolava due operazioni logicamente distinte: (1) la sostituzione delle variabili locali e (2) la navigazione globale dell'IR. Questo rendeva il codice fragile e difficile da ragionare, con il RefCell dello stack condiviso attraverso tutto il traversal.

2.3 La Soluzione: Separazione in Due Fasi

L'intuizione chiave viene dalla teoria dei compilatori: nella compilazione per fasi (multi-pass compilation), ogni passo ha una responsabilità limitata. Analogamente, separando la costruzione dell'intento (cosa vuole il codice) dalla valutazione dell'intento (dove porta quell'intento nell'IR), si ottengono vantaggi fondamentali:

Fondamento Teorico: Lazy Evaluation Applicata alla Risoluzione

La Query algebrica è concettualmente una thunk — un'espressione non ancora valutata che cattura l'intento del programmatore. Come nell'evaluazione lazy dei linguaggi funzionali, la valutazione viene rinviata al momento in cui tutto il contesto è disponibile. Questo elimina il problema dei forward-references per costruzione: quando l'Executor valuta le query, l'intero IR è già stato letto e indicizzato nel Scope Tree.

Fase 2a: Query Building (Substitution) — builder.rs

Responsabilità unica: eliminare le variabili locali dall'IR, sostituendole con espressioni algebriche (Query) che catturano l'intento di risoluzione senza eseguirlo. Usa il SymbolStack come ambiente effimero.

Invariante: dopo questa fase, l'IR non contiene più TypeRef::Unresolved — tutti sono diventati TypeRef::ResolutionQuery.

Fase 2b: Query Execution (Navigation) — executor.rs

Responsabilità unica: valutare algebricamente ogni Query navigando l'IR completo (tramite il Scope Tree), classificando il risultato in Resolved, External, Primitive, o Failed.

Invariante: dopo questa fase, l'IR non contiene più TypeRef::ResolutionQuery — tutti sono stati classificati.

3. L'Algebra delle Query (𝒬)

Riferimento: src/model/queries.rs:1-15

L'intuizione fondamentale dell'architettura v3 è che ogni operazione di risoluzione può essere espressa come composizione di sole tre primitive. Queste primitive catturano le due direzioni di navigazione possibili in un grafo gerarchico (salire e scendere) più l'operazione di invocazione.

pub enum Query {
    /// Find-going-up: cerca un componente risalendo lo scope.
    Find(String),
    /// Find-going-down: dato il risultato di una sub-query, scendi al membro.
    Extract(Box<Query>, String),
    /// Invoca la sub-query come funzione e restituisci il tipo di ritorno.
    Call(Box<Query>),
}

3.1 Query::Find — Ricerca Ascendente (find-going-up)

Find("X") è il punto di partenza di quasi ogni query. Semanticamente dice: "cerca un componente chiamato X partendo dal mio contesto attuale e risalendo verso la root finché non lo trovi".

Perché "risalendo"? Perché il lexical scoping funziona così: se scrivi Veicolo dentro una funzione che è dentro un modulo core, il compilatore cerca prima Veicolo nello scope della funzione, poi nello scope del modulo core, poi nello scope del modulo root. Trova il primo match e si ferma.

Perché solo il nome semplice, non il path completo? Perché i path multi-segmento (a.b.T) sono scomposti dal Builder in catene di Extract. Find riceve sempre e solo il primo segmento.

3.2 Query::Extract — Discesa di un Livello (find-going-down)

Extract(Q, "Y") dice: "valuta Q per ottenere un componente, poi cerca il membro Y al suo interno". È l'operatore di accesso ai membri (. o ::).

Perché Box<Query>? Perché Extract contiene ricorsivamente un'altra query. In Rust, i tipi ricorsivi devono essere allocati sullo heap tramite Box per avere una dimensione nota a compile-time.

Perché la composizione è lineare? Un path come a.b.c.d diventa Extract(Extract(Extract(Find("a"), "b"), "c"), "d"). L'annidamento cresce linearmente con il numero di segmenti. Questo è intenzionale: ogni livello di Extract corrisponde a un passo di discesa nell'albero dei componenti.

3.3 Query::Call — Invocazione e Tipo di Ritorno

Call(Q) dice: "valuta Q, trattalo come una funzione, e restituisci il suo tipo di ritorno". È ciò che abilita le catene di chiamate.

Perché è necessario? Consideriamo a.f().g():

  • a.f() restituisce un oggetto di tipo T (il return type di f)
  • .g() deve essere cercato nei metodi di T, non nei metodi di a

Senza Call, non c'è modo di esprimere "il risultato di una chiamata". L'Executor, quando incontra Call all'interno di un Extract, consulta il Scope Tree per il tipo di ritorno della funzione, permettendo la risoluzione transitiva.

3.4 Perché Tre Primitive Sono Sufficienti

Ogni espressione di accesso in un linguaggio di programmazione può essere scomposta in sequenze di:

  1. Partenza — trovare un punto iniziale nello scope (Find)
  2. Navigazione — scendere di un livello alla volta (Extract)
  3. Invocazione — passare attraverso una chiamata di funzione (Call)

Non servono primitive aggiuntive perché l'analizzatore opera a livello architetturale, non a livello di espressioni arbitrarie. Non deve valutare operatori aritmetici, condizioni, o flussi di controllo — deve solo tracciare da dove vengono i tipi.

3.5 Esempi di Composizione

Espressione sorgente → Query algebrica generata dal Builder ① Nome semplice: Veicolo → Find("Veicolo") Nessuna variabile locale trovata nello stack → Find generico. ② Path qualificato: std::io::File → Extract(Extract(Find("std"), "io"), "File") Il primo segmento diventa Find, ogni segmento successivo diventa Extract. ③ Accesso a membro di variabile locale: db.query() → Call(Extract(Find("Db"), "query")) Se "db" è una variabile locale di tipo Db (registrata nello stack come Find("Db")), lo stack SOSTITUISCE "db" con Find("Db"). Poi .query → Extract(..., "query"), poi () → Call(...). ④ Catena di chiamate: a.f().g() → Call(Extract(Call(Extract(Find("A"), "f")), "g")) a → Find("A") [sostituzione] .f() → Call(Extract(Find("A"), "f")) ↑ questo Call produce il TIPO DI RITORNO di f() .g() → Call(Extract([tipo_ritorno_f], "g")) ⑤ self/this: self.get_id() → Call(Extract(Find("Veicolo"), "get_id")) "self" è registrato dal Builder come Find("Veicolo") quando si entra nel StructuredType "Veicolo". ⑥ Costruttore: Db::new() → Call(Extract(Find("Db"), "new")) Il Builder trasforma calls con is_call=true → wrapping in Call. ⑦ Istanziazione: Auto { ... } → Find("Auto") Le istanziazioni (instantiates) usano is_call=false → niente Call wrapper.

3.6 Il Flag is_call in substitute_type

La funzione substitute_type accetta un parametro booleano is_call. Questo determina se la query finale deve essere wrappata in Call(...):

  • is_call = true: usato per gli elementi nel campo block.calls — sono chiamate a funzione, vogliamo tracciare la funzione stessa come dipendenza
  • is_call = false: usato per tutto il resto — tipi dei campi, parametri, tipi di ritorno, istanziazioni, dichiarazioni

Motivazione: la distinzione serve nella Fase 3 (Dependency Graph) per generare archi semanticamente diversi (un Calls vs un UsesFieldType). Ma già nella Fase 2, il wrapping in Call influenza come l'Executor valuta la query (vedi sezione 7.3).

4. L'Environment (ρ): Il Symbol Stack

Riferimento: src/resolver/stack.rs:1-67

4.1 Fondamento Teorico

Dalla formalizzazione LaTeX (cap. Costruzione e Risoluzione delle Query Architetturali), l'ambiente lessicale è modellato come:

Definizione formale: L'Environment ρ è definito come uno stack di frame:
ρ = ⟨Σ₀, Σ₁, ..., Σₙ⟩
Ogni frame Σₖ = ⟨Symbols, I_imports⟩ rappresenta un singolo livello di annidamento lessicale. Lo stack cresce verso l'alto: Σₙ è il frame corrente (top), Σ₀ è il frame globale (bottom).

Perché uno stack e non un albero? Perché durante il traversal dell'IR, il resolver visita un solo "ramo" dell'albero alla volta. Lo stack modella esattamente il percorso dalla root allo scope corrente. Quando il traversal esce da uno scope (pop) ed entra nel fratello successivo (push), il nuovo frame riutilizza la stessa posizione nello stack — nessun nodo permanente viene allocato.

4.2 Struttura di StackFrame

pub struct StackFrame {
    pub symbols: HashMap<String, Query>,  // nome semplice → Query di sostituzione
    pub imports: Vec<Import>,             // jump points disponibili in questo scope
}

Evoluzione della mappa symbols attraverso le versioni

VersioneTipo della mappaCosa rappresenta
v1 (Arena)HashMap<Identifier, Component>Possedeva l'intero componente IR clonato — costoso e fragile
v2 (Monofase)HashMap<String, QualifiedName>Percorso assoluto — sufficiente per risoluzione diretta, ma non per catene
v3 (Bifase)HashMap<String, Query>Query algebrica — cattura l'intento, non il risultato. Abilita catene e lazy evaluation

Il cambiamento da QualifiedName a Query è il cuore della transizione v2→v3. Nella v2, quando si registrava v → ["root","core","Veicolo"], il percorso era già risolto. Ma per risolvere v.id, bisognava concatenare stringhe: ["root","core","Veicolo","id"]. Se il percorso conteneva una catena di chiamate (es. v.f().id), non c'era modo di esprimerlo come una semplice concatenazione. Con Query, si registra v → Find("Veicolo") e poi v.f().id diventa Extract(Call(Extract(Find("Veicolo"), "f")), "id") — composizione naturale.

4.3 API Completa del SymbolStack

4.4 Perché RefCell?

Il BuilderContext contiene un &RefCell<SymbolStack>. Questo è necessario per un motivo specifico di Rust:

Il Builder attraversa l'IR con funzioni ricorsive (build_module_queries, build_structured_type_queries, ecc.) che condividono tutte lo stesso stack. In Rust, passare un &mut SymbolStack a una funzione che poi chiama altre funzioni con lo stesso riferimento mutabile viola le regole del borrow checker (una sola &mut alla volta).

RefCell sposta il controllo dal compile-time al runtime: permette di prendere il borrow mutabile (borrow_mut()) solo quando serve, rilasciandolo subito dopo. Questo è sicuro perché:

  • Ogni borrow_mut() nel codice è una singola operazione atomica (insert, push, pop)
  • Non ci sono mai due borrow_mut() simultanei — il borrow viene rilasciato prima della prossima operazione

5. Fase 2a: Query Building (builder.rs)

Riferimento: src/resolver/builder.rs:1-150

5.1 La Funzione substitute_type — Analisi Riga per Riga

Questa è la funzione più importante della Fase 2a. Ogni TypeRef dell'IR passa attraverso di essa.

fn substitute_type(ctx: &BuilderContext, tr: TypeRef, is_call: bool) -> TypeRef {
    match tr {
        TypeRef::Unresolved(qn) if !qn.is_empty() => {

Riga 1: Pattern matching su tr. Processa solo i TypeRef::Unresolved non vuoti. Tutti gli altri stati (Primitive, già Resolved, ecc.) passano inalterati — il Builder non li tocca.

Perché il guard if !qn.is_empty()? Per protezione contro path vuoti che il parser potrebbe generare in casi degeneri. Un Unresolved([]) non ha significato e viene ignorato.

            let first = &qn[0];
            let mut base_query = if let Some(local_query) = ctx.stack.borrow()
                .frames.iter().rev()
                .find_map(|f| f.symbols.get(first))
            {
                local_query.clone()   // SOSTITUZIONE AVVENUTA
            } else {
                Query::Find(first.clone())  // NESSUNA SOSTITUZIONE
            };

Righe 2-8: Il cuore della sostituzione lessicale. Il primo segmento del path (qn[0]) viene cercato nello SymbolStack top-down (.iter().rev()). Due esiti:

  • Match trovato: il primo segmento è una variabile locale (es. v) il cui tipo è stato registrato come query (es. Find("Veicolo")). La query registrata sostituisce il nome della variabile. Questo è il meccanismo che "elimina" le variabili locali dall'IR.
  • Nessun match: il primo segmento non è una variabile locale — è un nome di tipo "puro" (es. Veicolo). Viene wrappato in Query::Find(name), che delega la risoluzione alla Fase 2b.

Concetto chiave: Variable Shadowing

L'iterazione iter().rev() (dall'alto verso il basso) garantisce che una variabile definita in uno scope interno nasconda (shadow) una variabile con lo stesso nome in uno scope esterno. Questo è il comportamento standard del lexical scoping. Esempio: se un parametro v nella funzione ha lo stesso nome di un tipo v nel modulo, il parametro (frame più in alto) viene trovato per primo.

            for part in qn.into_iter().skip(1) {
                base_query = Query::Extract(Box::new(base_query), part);
            }

Righe 9-11: Per ogni segmento rimanente del path, si aggiunge un livello di Extract. Se il path originale era ["a", "b", "T"], si produce Extract(Extract(Find("a"), "b"), "T").

            if is_call {
                base_query = Query::Call(Box::new(base_query));
            }
            TypeRef::ResolutionQuery(base_query)

Righe 12-14: Se is_call == true, la query viene wrappata in Call(...). Infine, la query costruita viene emessa come TypeRef::ResolutionQuery.

5.2 Iniezione di self e this

All'ingresso di ogni StructuredType, il Builder registra due simboli speciali:

let self_query = Query::Find(st.name.last().unwrap_or(&"".to_string()).clone());
ctx.stack.borrow_mut().define_symbol("self".to_string(), self_query.clone());
ctx.stack.borrow_mut().define_symbol("this".to_string(), self_query);

Perché st.name.last()? Perché il nome del tipo strutturato nell'IR prima della Fase 2b è un nome relativo (es. ["Veicolo"]), non assoluto (che diventerà ["root","core","Veicolo"] solo nell'Executor). .last() estrae "Veicolo".

Perché si inietta self_keyword? Per supportare l'accesso ai membri d'istanza. A seconda della configurazione del linguaggio (self_keyword), il Builder inietta dinamicamente la keyword corretta (es. self per Rust, this per Java/C#). Python, invece, non utilizza una keyword hardcoded a livello di classe, ma si affida all'euristica implicit_first_param_as_self che mappa dinamicamente il primo parametro dei metodi all'istanza della classe.

Cosa succede per gli ImplBlock? Stessa logica, ma la keyword punta alla query del impl_for (cioè il tipo per cui l'impl è definito), non al nome dell'impl block stesso.

5.3 Registrazione dei Parametri — Perché Solo ResolutionQuery

ff.signature.parameters = ff.signature.parameters.into_iter().map(|mut p| {
    p.ty = substitute_type(ctx, p.ty, false);
    if let Some(name) = &p.name {
        if let TypeRef::ResolutionQuery(ref q) = p.ty {
            ctx.stack.borrow_mut().define_symbol(name.clone(), q.clone());
        }
    }
    p
}).collect();

Il parametro viene prima sostituito (substitute_type), poi, solo se il tipo risultante è un ResolutionQuery, viene registrato nello stack.

Perché solo ResolutionQuery? Se il tipo del parametro era già Primitive (es. int) o Resolved, non c'è nulla da "risolvere" — la variabile non aggiunge informazione utile per le sostituzioni successive. In pratica, dopo substitute_type, quasi tutti i tipi diventano ResolutionQuery (perché l'estrazione produce Unresolved), quindi questo guard cattura il 95%+ dei casi.

5.4 Differenza tra calls e instantiates

block.calls = block.calls.into_iter().map(|c| substitute_type(ctx, c, true)).collect();
block.instantiates = block.instantiates.into_iter().map(|i| substitute_type(ctx, i, false)).collect();

Le calls usano is_call = true (producono Call(…)), le instantiates usano is_call = false. La ragione è semantica:

  • db.query() è una chiamata → l'arco di dipendenza punta alla funzione query
  • Auto { ... } è un'istanziazione → l'arco punta al tipo Auto

6. Lo Scope Tree (Arena Allocator)

Riferimento: src/resolver/scope.rs:1-120

6.1 A Cosa Serve — Rappresentazione Esatta del Lexical Scoping

Lo Scope Tree è una struttura ad albero che mappa fedelmente l'annidamento lessicale del codice sorgente. Viene costruito all'inizio della Fase 2b (prima di qualsiasi risoluzione) leggendo l'IR prodotto dalla Fase 2a.

A differenza del vecchio Global Registry (che era un dizionario piatto di percorsi assoluti), lo Scope Tree permette all'Executor di fare Lexical Climbing (risalita dello scope) vero e proprio. Quando l'Executor cerca un identificatore, parte dal nodo corrente dell'albero e sale di padre in padre fino a trovare la definizione, esattamente come fa il compilatore Rust o Java.

6.2 Allocazione tramite Arena (Vec<ScopeNode>)

In Rust, implementare un albero con riferimenti reciproci (padre-figlio) usando puntatori come Rc<RefCell<T>> è lento e prono a memory leak. Per questo usiamo un Arena Allocator:

pub struct ScopeTree {
    pub arena: Vec<ScopeNode>,
    pub root: ScopeId,
}

pub struct ScopeNode {
    pub id: ScopeId,
    pub parent: Option<ScopeId>,
    pub children: HashMap<String, ScopeId>,
    pub full_path: QualifiedName,
    pub return_type: Option<TypeRef>,
}

Come funziona: Ogni nodo è semplicemente salvato in un array lineare (Vec). Un ScopeId è solo un indice (usize) in questo array. Questo rende l'accesso O(1), senza overhead di puntatori, ed è cache-friendly.

6.3 Costruzione: build_scope_tree Passo per Passo

La funzione attraversa l'IR ricorsivamente e popola l'Arena. Ad ogni livello crea un nuovo ScopeNode, imposta il suo parent al nodo chiamante, e registra se stesso nei children del padre.

I 5 passi della costruzione (executor.rs)

Passo 1 — Il modulo stesso: Crea un nodo per il modulo, aggiungilo ai children del padre. Passo 2 — I tipi strutturati: Per ogni st in m.structured_types: Crea nodo per st, ricorsione per i metodi e nested_types. Passo 3 — Le funzioni libere: Crea nodo per ogni funzione. Salva il suo `return_type` nel nodo! Questo abilita l'inferenza per le catene di chiamate. Passo 4 — Gli impl blocks: Per ogni ib in m.impl_blocks: Trova o crea il nodo del target_name (es. "Veicolo"). Per ogni metodo, crea un nodo figlio sotto "Veicolo" con il suo return_type. Passo 5 — I sotto-moduli (ricorsione): Per ogni sub in m.sub_modules: ricorsione nel sotto-modulo.

6.4 Le API dell'Albero: find_child e get_node

  • get_node(id): restituisce una reference al nodo. O(1).
  • find_child(id, name): cerca "name" tra i figli diretti del nodo id. O(1).

7.2 evaluate_typeref — La Funzione di Classificazione

Questa funzione è il punto d'ingresso per la risoluzione di ogni singolo TypeRef:

fn evaluate_typeref(ctx: &ExecutorContext, tr: TypeRef) -> TypeRef {
    match tr {
        TypeRef::ResolutionQuery(query) => {
            if let Some(res) = evaluate_query(ctx, &query, false) {
                // La query ha prodotto un path. Ma è locale o esterno?
                if ctx.registry.exists(&res) {
                    TypeRef::Resolved(res)      // ✅ Trovato nel progetto
                } else {
                    TypeRef::External(res)      // ⚠️ Path costruito ma non locale
                }
            } else {
                // La query ha fallito completamente. Ultimo tentativo: è un primitivo?
                let name = extract_base_name(&query);
                if ctx.primitives.is_primitive(&name) {
                    TypeRef::Primitive(PrimitiveType::Other(name))
                } else {
                    TypeRef::Failed(vec![name]) // ❌ Non trovato
                }
            }
        }
        _ => tr,  // Già Resolved/External/Primitive/Failed → passthrough
    }
}

Nota critica sull'ordine di priorità:

  1. Prima si tenta la risoluzione algebrica (evaluate_query)
  2. Se produce un path → si verifica esistenza nel registry
  3. Se la query fallisce → si tenta il primitivo
  4. Se anche il primitivo fallisce → Failed

Perché evaluate_query è chiamata con resolve_call_return: false? Perché a questo livello top-level, per un Call(Find("f")), vogliamo l'arco di dipendenza verso la funzione stessa, non verso il suo tipo di ritorno. Il tipo di ritorno serve solo internamente quando Call è genitore di un Extract in una catena.

7.3 evaluate_query — Il Motore Algebrico (Deep Dive)

7.3.1 Query::Find — L'Algoritmo di Lexical Scope Climbing

Questa è la funzione più complessa dell'Executor. Implementa il "find-going-up" — la risalita lessicale:

Query::Find(name) => {
    let mut prefix = ctx.current_prefix.clone();
    loop {
        // 1. Costruisci candidato: prefix + name
        let mut candidate = prefix.clone();
        candidate.push(name.clone());
        if ctx.registry.exists(&candidate) {
            return Some(candidate);  // TROVATO nel registry!
        }

        // 2. Controlla gli import a TUTTI i livelli
        for level_imports in ctx.imports_stack.iter().rev() {
            for imp in level_imports {
                if let Some(alias) = &imp.alias {
                    if alias == name { return Some(imp.path.clone()); }
                } else if let Some(last) = imp.path.last() {
                    if last == name { return Some(imp.path.clone()); }
                }
            }
        }

        // 3. Risali di un livello
        if prefix.is_empty() { break; }
        prefix.pop();
    }

    // 4. Fallback assoluti
    let direct = vec![name.clone()];
    if ctx.registry.exists(&direct) { return Some(direct); }
    let root_cand = vec!["root".to_string(), name.clone()];
    if ctx.registry.exists(&root_cand) { return Some(root_cand); }

    None  // Non trovato da nessuna parte
}

Esempio dettagliato: Risolvere Find("Veicolo") dal contesto ["root","core","calcola"]:

Iterazione 1: prefix = ["root", "core", "calcola"] candidate = ["root", "core", "calcola", "Veicolo"] registry.exists? → ❌ No imports check: nessun match a nessun livello prefix.pop() → ["root", "core"] Iterazione 2: prefix = ["root", "core"] candidate = ["root", "core", "Veicolo"] registry.exists? → ✅ Sì! → return Some(["root", "core", "Veicolo"])

Perché il fallback ["root", name]?

In molti linguaggi, il modulo principale del progetto si chiama "root" nell'IR. Se il lexical scope climbing non trova nulla, l'ultimo tentativo è cercare direttamente sotto root. Questo gestisce il caso in cui un tipo viene referenziato da un contesto il cui prefix non include "root" (es. perché il contesto è a livello globale con prefix vuoto []).

7.3.2 Query::Extract — Discesa e Method Resolution Order (MRO)

Query::Extract(parent_query, member_name) => {
    let parent_path = evaluate_query(ctx, parent_query, true)?;
    
    // Funzione interna per ricerca ricorsiva (con cycle detection)
    fn find_member(ctx, current_path, member, visited) -> Option<QualifiedName> {
        let mut candidate = current_path.clone();
        candidate.push(member.clone());
        // 1. Match diretto
        if ctx.registry.exists(&candidate) { return Some(candidate); }

        // Cycle check per evitare loop infiniti in MRO ciclici
        let check_cycles = ctx.current_lang.as_deref()
            .map(|l| ctx.config.get_for(l).cyclic_mro_check)
            .unwrap_or(true);
        if check_cycles && !visited.insert(current_path.clone()) {
            return None; // Ciclo rilevato
        }

        let entry = ctx.registry.get(&current_path);

        // 2. Transitive Imports Fallback (se il target è un modulo)
        let allow_transitive = ctx.current_lang.as_deref()
            .map(|l| ctx.config.get_for(l).transitive_imports)
            .unwrap_or(false);
        if allow_transitive {
            if let Some(RegistryEntry::Module { imports }) = entry {
                for imp in imports {
                    if imp.is_wildcard {
                        if let Some(found) = find_member(ctx, imp.path.clone(), member, visited) { return Some(found); }
                    } else if let Some(alias) = &imp.alias {
                        if alias == member { return Some(imp.path.clone()); }
                    } else if let Some(last) = imp.path.last() {
                        if last == member { return Some(imp.path.clone()); }
                    }
                }
            }
        }

        // 3. MRO: Depth-First, Left-to-Right
        if let Some(RegistryEntry::StructuredType { super_types }) = entry {
            for sup in super_types {
                if let TypeRef::ResolutionQuery(q) = sup {
                    if let Some(sup_path) = evaluate_query(ctx, q, true) {
                        if let Some(found) = find_member(ctx, sup_path, member, visited) { return Some(found); }
                    }
                }
            }
        }
        None
    }
    // ...
}

Questo operatore è il fulcro della Dynamic Dispatch statica e della Transitive Resolution. Svolge i seguenti compiti gerarchici:

  1. Se module.Foo o Cat.breathe esiste direttamente, viene restituito.
  2. Transitive Imports: Se il percorso esplorato è un Module e il linguaggio supporta gli import transitivi (es. Python), si ispezionano gli import esportati dal modulo (compresi quelli wildcard tramite ricorsione sicura controllata dal visited set) per trovare un match per il nome cercato, ri-mappando virtualmente il percorso a quello originale.
  3. Method Resolution Order: Se il percorso esplorato è un StructuredType (e la ricerca diretta è fallita), cerca nei super_types. Valuta la query del genitore (es. Animal) e cerca Animal::breathe. La ricorsione è Depth-First, Left-to-Right, bloccata su cicli in caso di MRO complessi.
  4. Garantisce il corretto linking alle implementazioni di default dei Trait in Rust o Interfacce Java, comportandosi come un vero compilatore.

7.3.3 Query::Call — Il Comportamento Duale

Query::Call(target_query) => {
    let target_path = evaluate_query(ctx, target_query, false)?;

    if resolve_call_return {
        // MODALITÀ CATENA: serve il tipo di ritorno
        if let Some(RegistryEntry::Function { return_type }) = ctx.registry.get(&target_path) {
            match return_type {
                TypeRef::ResolutionQuery(ret_q) => evaluate_query(ctx, ret_q, true),
                TypeRef::Resolved(qn) => Some(qn.clone()),
                TypeRef::External(qn) => Some(qn.clone()),
                TypeRef::Unresolved(qn) => Some(qn.clone()),
                _ => None,
            }
        } else { None }
    } else {
        // MODALITÀ ARCO: serve il path della funzione stessa
        Some(target_path)
    }
}

Il Parametro resolve_call_return — Spiegazione Profonda

Questo flag booleano è la chiave dell'intera architettura di inferenza. Ha due modalità:

  • false (default, usato da evaluate_typeref): Call(Find("f")) produce ["root","core","f"]. Il risultato è il path della funzione. Questo è ciò che serve per gli archi di dipendenza nel grafo (Fase 3).
  • true (usato da Extract quando il genitore è un Call): Call(Find("f")) consulta il Scope Tree per il return_type di f e restituisce il tipo di ritorno. Questo è ciò che serve per le catene: in f().g(), g va cercato nel tipo di ritorno di f, non in f stessa.

Perché il target_query è sempre valutato con false? Perché evaluate_query(ctx, target_query, false) produce il path della funzione — quello che serve per fare registry.get(path) e leggere il return_type. Se usassimo true, otterremmo il tipo di ritorno del target, che non è la funzione stessa!

Il caso ResolutionQuery(ret_q) nel return type: Se il tipo di ritorno della funzione è ancora una query (perché non è stato ancora risolto — siamo nel mezzo dell'esecuzione), viene valutato ricorsivamente con evaluate_query(ctx, ret_q, true). Questo permette catene arbitrariamente lunghe.

7.4 extract_base_name — Utilità per il Fallback

pub fn extract_base_name(query: &Query) -> String {
    match query {
        Query::Find(n) => n.clone(),
        Query::Extract(q, _) => extract_base_name(q),
        Query::Call(q) => extract_base_name(q),
    }
}

Discende ricorsivamente nella query fino a trovare il Find(name) alla base. Usata in due contesti: (1) in evaluate_typeref per il fallback primitivo, e (2) nel registry per estrarre il target name degli impl blocks.

8. Il Primitive Registry

Riferimento: src/resolver/primitives.rs:1-42

8.1 Motivazione: Decoppiamento Primitivo

Senza il PrimitiveRegistry, ogni tipo primitivo (String, int, bool, float) verrebbe marcato come Failed — non è definito nel progetto, non è importato da nessuna parte. Ma nel grafo delle dipendenze, un Failed può essere interpretato come un errore nell'analisi. Un campo name: String non è un errore — è un tipo primitivo del linguaggio.

8.2 Design Data-Driven e Language-Agnostic

pub fn load(lang_name: &str) -> anyhow::Result<Self> {
    let primitives_json = include_str!("../../primitives.json");
    let registry: HashMap<String, Vec<String>> = serde_json::from_str(primitives_json)?;
    let lang_primitives = registry.get(lang_name).cloned()
        .unwrap_or_default().into_iter().collect();
    Ok(Self { lang_primitives })
}

Perché include_str!? Il file JSON viene embedded nel binario a compile-time. Non serve un file esterno a runtime — il binario è autosufficiente.

Perché un file JSON e non codice Rust? Perché l'analizzatore è language-agnostic. Ogni linguaggio ha i suoi primitivi. Il JSON permette di aggiungere nuovi linguaggi senza ricompilare.

8.3 Perché il Primitivo Si Controlla per ULTIMO

Il check primitives.is_primitive(name) avviene solo dopo che evaluate_query ha fallito completamente. Questo ordine è intenzionale:

  • Se nel progetto esiste un tipo chiamato String (es. una classe custom), deve essere risolto come Resolved, non come Primitive
  • Se un import porta un tipo String da una libreria esterna, deve essere External
  • Primitive è il fallback ultimo — solo se il nome non è stato trovato da nessuna parte

Perché execute_block non crea un nuovo prefix?

I blocchi (Block) non sono componenti architetturali con un nome proprio. Un blocco if o while non appare nel grafo delle dipendenze come nodo. I blocchi contengono dichiarazioni e chiamate, ma queste vengono risolte nel contesto della funzione che le contiene. Per questo execute_block usa il ctx del genitore senza modificarlo.

Perché execute_impl_block usa il nome del tipo target, non dell'impl?

Se abbiamo impl Veicolo { fn new() ... }, il metodo new deve essere raggiungibile come ["root","core","Veicolo","new"]. Il prefix dell'impl block viene impostato al tipo target (es. ["root","core","Veicolo"]) così che i metodi al suo interno abbiano percorsi coerenti con i metodi definiti direttamente nella struct.

9.3 Name Rewriting — Un Effetto Collaterale Fondamentale

L'Executor, oltre a risolvere le query, ha un effetto collaterale importante: riscrive i nomi dei componenti da relativi ad assoluti.

// In execute_module:
m.name = new_prefix.clone();  // ["core"] → ["root", "core"]

// In execute_structured_type:
st.name = new_prefix.clone(); // ["Veicolo"] → ["root", "core", "Veicolo"]

// In execute_function:
f.name = new_prefix.clone();  // ["calcola"] → ["root", "core", "calcola"]

Questo name rewriting è necessario perché dopo la Fase 2, l'IR deve contenere solo percorsi assoluti. La Fase 3 (Dependency Graph) usa questi percorsi assoluti come identificatori univoci dei nodi del grafo.

10. Flattening degli Impl Blocks

Riferimento: src/resolver/executor.rs:45-63

Cos'è? In Rust, i metodi di una struct sono definiti in blocchi impl separati dalla definizione della struct. In Java/C#, i metodi sono definiti dentro la classe. L'analizzatore normalizza questa differenza fondendo i metodi degli impl blocks nelle struct target.

let mut unfused_impls = vec![];
for ib in m.impl_blocks {
    let mut fused = false;
    if let TypeRef::Resolved(ref target_name) = ib.impl_for {
        if let Some(target_st) = m.structured_types.iter_mut()
            .find(|st| &st.name == target_name)
        {
            target_st.methods.extend(ib.methods.clone());
            target_st.nested_types.extend(ib.nested_types.clone());
            if let Some(trait_ref) = ib.implements_trait.clone() {
                target_st.super_types.push(trait_ref);
            }
            fused = true;
        }
    }
    if !fused { unfused_impls.push(ib); }
}
m.impl_blocks = unfused_impls;

Condizioni per la fusione:

  1. ib.impl_for deve essere TypeRef::Resolved — il tipo target è stato trovato nel progetto
  2. Il tipo target deve esistere nel campo m.structured_types dello stesso modulo

Perché preservare gli unfused? Un impl block per un tipo External (es. impl ExternalTrait for LocalType) non può essere fuso perché il tipo target non è nell'IR locale. I suoi metodi devono essere preservati per la Fase 3.

10.5 Forward Declarations e Out-Of-Line Methods

Riferimento: src/analyzer.rs:link_out_of_line_methods

Cos'è? In linguaggi come C++, è comune dichiarare un metodo all'interno di una classe (in un file header) e definirne il corpo esternamente usando il resolution operator (es. void MyClass::my_method() { ... }). Il parser Tree-sitter estrae la definizione out-of-line come una Function globale, disconnettendola dalla sua classe di appartenenza.

Per ricongiungere questi metodi, l'analizzatore esegue un passo di pre-processing (attivato dal flag forward_declarations nel LanguageConfig) prima che inizi la Name Resolution:

if config.get_for(lang).forward_declarations {
    let mut methods_to_move = vec![];
    
    // 1. Estrae le funzioni con nome qualificato (es. MyClass::my_method)
    module.free_functions.retain(|ff| {
        if ff.name.len() > 1 {
            methods_to_move.push(ff.clone());
            false // Rimuove dalle funzioni libere
        } else {
            true // Mantiene
        }
    });

    // 2. Ricolloca i metodi all'interno della rispettiva classe
    for method in methods_to_move {
        let class_name = &method.name[..method.name.len() - 1]; // "MyClass"
        let method_name = method.name.last().unwrap().clone();  // "my_method"
        
        // Cerca la classe nel modulo e inietta il metodo (aggiornando o sostituendo la dichiarazione)
        // ...
    }
}

Perché è importante? Senza questa fusione, il Query Engine non potrebbe iniettare la keyword this all'interno del corpo del metodo out-of-line (poiché verrebbe trattato come una funzione libera). Questo farebbe fallire la risoluzione di tutti gli accessi ai membri della classe (es. this->field) scritti all'interno del metodo.

Fase 1 (Estrazione CST → IR) Il parser estrae il nome testuale dal codice sorgente. └──→ TypeRef::Unresolved(["Veicolo"]) Fase 2a (Query Building — Substitution) Il Builder applica le regole di sostituzione dallo SymbolStack. Se "Veicolo" fosse una variabile locale, verrebbe espansa nella sua query associata. └──→ TypeRef::ResolutionQuery(Find("Veicolo")) Fase 2b (Query Execution — Navigation) L'Executor naviga l'IR valutando algebricamente la Query. ├──→ TypeRef::Resolved(["root", "core", "Veicolo"]) registry.exists = true ├──→ TypeRef::External(["ext", "db", "Database"]) import match, registry.exists = false ├──→ TypeRef::Primitive(Other("String")) query fallita, primitivo riconosciuto └──→ TypeRef::Failed(["UnknownType"]) query fallita, non primitivo Fase 3 (Dependency Graph) I TypeRef classificati generano archi nel grafo architetturale. ├──→ Resolved → arco verso nodo interno (Inherits, UsesFieldType, Calls, Instantiates) ├──→ External → arco verso confine esterno (stessa classificazione semantica) ├──→ Primitive → ignorato (non è una dipendenza architetturale) └──→ Failed → nessun arco generato (dipendenza persa)

13. Gestione Modulare Agnostica (Module Strategies)

I linguaggi di programmazione presentano differenze architetturali profonde nella definizione e organizzazione dei moduli. Per gestire questa diversità senza intaccare l'agnosticismo dell'albero degli scope, il motore fa affidamento su un sistema di strategie combinabili, rappresentate da feature flags booleane. Questa architettura consente di sovrapporre più comportamenti per linguaggi complessi.

Strategia (Flag)Descrizione e ComportamentoEs. Linguaggio
file_basedOgni file fisico sorgente viene trattato come un modulo isolato. Il nome del file (senza estensione) funge da identificatore del modulo.Rust, Python, Go
directory_basedLe directory fisiche vengono convertite in moduli padre, annidando i moduli dei file in base alla struttura della cartella.Rust, Python
package_decl_basedIl file viene scannerizzato per dichiarazioni di pacchetto esplicite a livello di file (es. package org.example;). Il contenuto viene collocato all'interno di questo percorso logico.Java, Go
namespace_basedIl sistema supporta blocchi di namespace testuali espliciti annidati (es. namespace X { ... }). In questo modello un singolo file può contenere frammenti di più moduli/namespace logici.C++, C#
inline_mod_basedIl codice supporta la definizione di moduli inline all'interno del file, che fungono da delimitatori di scope (es. mod tests { ... } in Rust).Rust

Perché il cambio di architettura?

Il modello monofase richiedeva che tutto fosse risolvibile nell'ordine in cui il traversal incontra i nodi. Questo rendeva impossibili i forward-references e le catene di chiamate. La Query algebrica funge da lazy evaluation — cattura l'intento del programmatore senza eseguirlo, rinviando la valutazione al momento in cui tutto il contesto è disponibile.

Formalmente, la transizione da v2 a v3 corrisponde al passaggio da una valutazione eager (risolvi subito) a una valutazione deferred (costruisci la query, valutala dopo). Questo è lo stesso principio usato nei compilatori moderni che separano la fase di type-checking (analisi semantica) dalla fase di code generation.

6. Estensioni Architetturali (Aliases, Casts, e Unions)

L'architettura del resolver è progettata per gestire in modo trasparente pattern complessi tipici della programmazione moderna:

6.1 Type Aliases

Gli Alias di tipo (es. type MyString = String) vengono rappresentati nello Scope Tree tramite Symbol::TypeAlias(TypeRef). Durante la fase 2b (Execution), quando il risolutore incontra un simbolo di questo genere:

  • Se la query originaria richiede di risolvere il "tipo" dell'entità, il TypeAlias viene automaticamente valutato sostituendolo con il TypeRef originario.
  • Questo meccanismo di indirezione trasparente assicura che gli alias abbiano l'identico comportamento dei tipi nativi senza che le funzioni chiamanti debbano gestire l'espansione.

6.2 Type Casts

I Type Casts (es. (int) x oppure x as i32) vengono intercettati a livello di Block dall'estrattore euristico e memorizzati in un vettore type_casts. La fase 2b li attraversa e risolve ogni cast generato come farebbe con un parametro o un valore di ritorno locale. Nel grafo finale, ogni cast si traduce in una dipendenza semantica di tipo CastsTo.

6.3 Union Types

I Tipi Unione (es. Union[str, int] o str | int) sono catturati dalla rappresentazione TypeRef::Union(Vec<TypeRef>). Poiché un'entità può assumere tipi multipli contemporaneamente:

  • Il resolver esplora e risolve indipendentemente ogni TypeRef interno al costrutto Union.
  • Durante la generazione del grafo architetturale, le dipendenze per nodi e riferimenti associati a costrutti Union (ad esempio un metodo invocato su una variabile dal tipo Unione) vengono moltiplicate o distinte per mappare ogni possibile target senza perdere precisione.
