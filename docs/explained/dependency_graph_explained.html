1. Panoramica e Posizione nella Pipeline

La Fase 3 (Costruzione del Dependency Graph) è il terzo stadio della pipeline. Riceve in input i moduli dell'IR con tutti i TypeRef già risolti dalla Fase 2 e produce in output un DependencyGraph — una struttura composta da nodi (i componenti del codice) e archi (le relazioni tra essi).

1. Estrazione CST→IR → 2. Name Resolution → 3. Dependency Graph → 4. Summary

Riferimento: analyzer.rs:104 — let graph = crate::export::graph::build_dependency_graph(&resolved);

Il grafo è la rappresentazione finale dell'architettura del codice. Può essere:

  • Serializzato in JSON per analisi programmatica
  • Esportato in formato Cytoscape per visualizzazione interattiva
  • Analizzato per metriche (accoppiamento, coesione, componenti connesse, ecc.)

Il processo si divide in due fasi logiche eseguite in sequenza:

A. Flatten Nodi → B. Genera Archi → DependencyGraph { nodes, edges }

2. Strutture Dati del Grafo

Riferimento: ir.rs:110-141

2.1 DependencyGraph

pub struct DependencyGraph {
    pub nodes: Vec<Component>,   // Tutti i componenti appiattiti
    pub edges: Vec<Dependency>,  // Tutte le relazioni tra componenti
}

2.2 Component — I nodi del grafo

pub enum Component {
    Module(Module),
    StructuredType(StructuredType),
    Function(Function),
}

Ogni componente del codice (modulo, tipo strutturato, funzione) diventa un nodo nel grafo. I nodi sono identificati dal loro QualifiedName (nome assoluto calcolato dalla Fase 2).

2.3 Dependency — Gli archi del grafo

pub struct Dependency {
    pub from: QualifiedName,       // Nodo sorgente (chi dipende)
    pub to: QualifiedName,         // Nodo target (da chi dipende)
    pub kind: DependencyEdgeKind,  // Tipo di relazione
}

2.4 DependencyEdgeKind — Tipologie di relazione

pub enum DependencyEdgeKind {
    Inherits,            // Ereditarietà (extends, super_types)
    Implements,          // Implementazione (impl for, implements)
    UsesFieldType,       // Tipo di un campo
    UsesParamType,       // Tipo di un parametro
    UsesReturnType,      // Tipo di ritorno
    NestedIn,            // Contenimento (metodo in struct, nested type)
    ModuleContainment,   // Contenimento (componente in modulo)
    Calls,               // Chiamata a funzione
    Instantiates,        // Istanziazione (new, struct expression)
}

I 9 tipi di arco si dividono in quattro categorie logiche:

CategoriaArchiSignificato
Strutturale ModuleContainment, NestedIn Relazione gerarchica "chi contiene chi"
Ereditarietà Inherits, Implements Relazione di sotto-tipizzazione
Type-Level UsesFieldType, UsesParamType, UsesReturnType Dipendenza tramite riferimento a un tipo
Comportamentale Calls, Instantiates Dipendenza tramite invocazione o costruzione

3. Entry Point: build_dependency_graph

Riferimento: export/graph.rs:4-13

pub fn build_dependency_graph(modules: &[Module]) -> DependencyGraph {
    // Fase A: Appiattisci tutti i componenti in un vettore di nodi
    let nodes = flatten_modules(modules);

    // Fase B: Genera tutti gli archi attraversando i moduli
    let mut edges = vec![];
    for m in modules {
        traverse_module_for_edges(m, None, &mut edges);
    }

    DependencyGraph { nodes, edges }
}

La funzione è breve ma nasconde due processi complessi:

  • Fase A (flatten_modules) — Raccoglie tutti i componenti (moduli, tipi, funzioni) dalla struttura gerarchica dell'IR e li appiattisce in un vettore lineare.
  • Fase B (traverse_module_for_edges) — Attraversa ricorsivamente la gerarchia dell'IR generando gli archi di dipendenza per ogni relazione trovata.

4. Fase A — Flattening dei Nodi (flatten_modules)

Riferimento: export/graph.rs:201-221

L'IR è una struttura gerarchica ad albero (moduli contengono struct, struct contengono metodi, ecc.). Il grafo delle dipendenze necessita invece di un elenco piatto di nodi. La funzione flatten_modules appiattisce ricorsivamente la gerarchia.

fn flatten_modules(modules: &[Module]) -> Vec<Component> {
    let mut flat = vec![];
    for m in modules {
        // 1. Il modulo stesso diventa un nodo
        flat.push(Component::Module(m.clone()));

        // 2. Ogni tipo strutturato (e i suoi annidamenti) diventa nodo
        for st in &m.structured_types {
            flat.extend(flatten_structured_type(st));
        }

        // 3. Ogni funzione libera diventa un nodo
        flat.extend(m.free_functions.iter().cloned().map(Component::Function));

        // 4. Ricorsione nei sotto-moduli
        flat.extend(flatten_modules(&m.sub_modules));
    }
    flat
}

fn flatten_structured_type(st: &StructuredType) -> Vec<Component> {
    let mut flat = vec![Component::StructuredType(st.clone())];

    // I metodi della struct diventano nodi Function
    flat.extend(st.methods.iter().cloned().map(Component::Function));

    // Ricorsione nei tipi annidati
    for nested in &st.nested_types {
        flat.extend(flatten_structured_type(nested));
    }
    flat
}
Cosa viene appiattito: Il flattening produce nodi per: ogni modulo, ogni tipo strutturato (inclusi i nested), ogni metodo, e ogni funzione libera. Ciò che non diventa nodo: i campi (Field), i parametri (Parameter), gli import, e gli impl blocks (che sono già stati fusi nella Fase 2).

4.1 Esempio di Flattening

Data la seguente struttura IR:

Module "root" ├── Module "core" │ ├── StructuredType "Veicolo" │ │ └── method "accelera()" │ └── StructuredType "Auto" │ ├── method "avvia()" │ └── nested StructuredType "Motore" └── Function "main()"

Il flattening produce il seguente vettore piatto di nodi:

nodes = [ Module("root"), Module("core"), StructuredType("Veicolo"), Function("accelera()"), StructuredType("Auto"), Function("avvia()"), StructuredType("Motore"), ← nested type appiattito Function("main()"), ]

5. Fase B — Generazione degli Archi

Riferimento: export/graph.rs:15-58

La seconda fase attraversa ricorsivamente l'IR generando un arco Dependency per ogni relazione tra componenti. La funzione principale è traverse_module_for_edges.

fn traverse_module_for_edges(
    m: &Module,
    parent_id: Option<&QualifiedName>,
    edges: &mut Vec<Dependency>,
) {
    // 1. Arco di contenimento modulo→modulo (se ha un genitore)
    if let Some(parent) = parent_id {
        edges.push(Dependency {
            from: parent.clone(),
            to: m.name.clone(),
            kind: DependencyEdgeKind::ModuleContainment,
        });
    }

    // 2. Per ogni tipo strutturato: arco contenimento + archi interni
    for st in &m.structured_types {
        edges.push(Dependency {
            from: m.name.clone(), to: st.name.clone(),
            kind: DependencyEdgeKind::ModuleContainment,
        });
        traverse_structured_type_edges(st, edges);
    }

    // 3. Per ogni funzione libera: arco contenimento + archi interni
    for ff in &m.free_functions {
        edges.push(Dependency {
            from: m.name.clone(), to: ff.name.clone(),
            kind: DependencyEdgeKind::ModuleContainment,
        });
        add_function_edges(ff, edges);
    }

    // 4. Per ogni impl block residuo: arco contenimento + archi interni
    for ib in &m.impl_blocks {
        edges.push(Dependency {
            from: m.name.clone(), to: ib.name.clone(),
            kind: DependencyEdgeKind::ModuleContainment,
        });
        add_impl_edges(ib, edges);
    }

    // 5. Ricorsione nei sotto-moduli
    for sub in &m.sub_modules {
        traverse_module_for_edges(sub, Some(&m.name), edges);
    }
}

Per ogni modulo, vengono generati:

  1. Un arco ModuleContainment dal genitore al modulo corrente (se esiste un genitore).
  2. Un arco ModuleContainment dal modulo a ciascun componente diretto (struct, funzioni, impl blocks).
  3. Gli archi interni di ciascun componente (delegati a funzioni specifiche).
  4. La ricorsione nei sotto-moduli, passando il nome del modulo corrente come parent_id.

6. Catalogo Completo dei Tipi di Arco

Tipo ArcoDa (from)A (to)Generato daQuando
ModuleContainment Modulo genitore Modulo, Struct, Funzione, Impl traverse_module_for_edges Sempre, per ogni componente diretto del modulo
NestedIn StructuredType o ImplBlock Metodo o Nested Type traverse_structured_type_edges, add_impl_edges Per ogni metodo e tipo annidato in un tipo strutturato
Inherits StructuredType Super type add_super_edges Per ogni TypeRef::Resolved o External in super_types
Implements ImplBlock Tipo target o Trait add_impl_edges Per impl_for e implements_trait se risolti
UsesFieldType StructuredType o Function Tipo del campo o variabile locale add_field_edges, add_block_edges Per ogni campo di un tipo strutturato, oppure per ogni dichiarazione di variabile locale nel body di una funzione (inclusi blocchi annidati), con TypeRef::Resolved o External
UsesParamType Function Tipo del parametro add_function_edges Per ogni parametro con tipo risolto
UsesReturnType Function Tipo di ritorno add_function_edges Se il tipo di ritorno è risolto
Calls Function Funzione/tipo chiamato add_block_edges Per ogni calls entry nel body della funzione (ricorsivamente nei sotto-blocchi) con tipo risolto
Instantiates Function Tipo istanziato add_block_edges Per ogni instantiates entry nel body della funzione (ricorsivamente nei sotto-blocchi) con tipo risolto
Regola fondamentale: Gli archi vengono generati solo per TypeRef::Resolved e TypeRef::External. I riferimenti Primitive, Unresolved e Failed vengono completamente ignorati — non generano archi. Questo significa che i tipi non risolti non producono dipendenze false nel grafo.

7. Le Funzioni di Generazione Archi in Dettaglio

7.1 traverse_structured_type_edges

Riferimento: graph.rs:60-81

fn traverse_structured_type_edges(st: &StructuredType, edges: &mut Vec<Dependency>) {
    // Archi Inherits per super_types
    add_super_edges(st, edges);

    // Archi UsesFieldType per i campi
    add_field_edges(st, edges);

    // Per ogni metodo: arco NestedIn + archi della funzione
    for m in &st.methods {
        edges.push(Dependency {
            from: st.name.clone(), to: m.name.clone(),
            kind: DependencyEdgeKind::NestedIn,
        });
        add_function_edges(m, edges);
    }

    // Per ogni tipo annidato: arco NestedIn + ricorsione
    for nested in &st.nested_types {
        edges.push(Dependency {
            from: st.name.clone(), to: nested.name.clone(),
            kind: DependencyEdgeKind::NestedIn,
        });
        traverse_structured_type_edges(nested, edges);  // Ricorsione
    }
}

Questa funzione è il punto di raccolta per tutte le dipendenze di un tipo strutturato. Genera archi per ereditarietà, campi, metodi e tipi annidati. Per i metodi e i nested types, genera prima un arco NestedIn (relazione strutturale), poi delega la generazione degli archi interni.

7.2 add_super_edges — Archi di ereditarietà

Riferimento: graph.rs:83-96

fn add_super_edges(st: &StructuredType, edges: &mut Vec<Dependency>) {
    for sup in &st.super_types {
        match sup {
            TypeRef::Resolved(to) | TypeRef::External(to) => {
                edges.push(Dependency {
                    from: st.name.clone(),
                    to: to.clone(),
                    kind: DependencyEdgeKind::Inherits,
                });
            }
            _ => {}  // Primitive, Unresolved, Failed → ignorati
        }
    }
}

Per ogni super-tipo (classe base, interfaccia implementata, trait), se il TypeRef è stato risolto, genera un arco Inherits. Notare che sia Resolved che External vengono processati — una classe può ereditare da un tipo esterno (es. una classe di una libreria).

7.3 add_field_edges — Archi dei campi

Riferimento: graph.rs:98-111

fn add_field_edges(st: &StructuredType, edges: &mut Vec<Dependency>) {
    for f in &st.fields {
        match &f.ty {
            TypeRef::Resolved(to) | TypeRef::External(to) => {
                edges.push(Dependency {
                    from: st.name.clone(),
                    to: to.clone(),
                    kind: DependencyEdgeKind::UsesFieldType,
                });
            }
            _ => {}
        }
    }
}

Per ogni campo del tipo strutturato, se il tipo del campo è risolto, genera un arco UsesFieldType. I campi con tipi primitivi (String, int, ecc.) o non risolti non generano archi.

7.4 add_function_edges — Archi dalla firma di una funzione

Riferimento: graph.rs:113-135

La funzione add_function_edges gestisce gli archi derivanti dalla firma della funzione (parametri e tipo di ritorno) e poi delega l'analisi del corpo a add_block_edges:

fn add_function_edges(ff: &Function, edges: &mut Vec<Dependency>) {
    // 1. Parametri → UsesParamType
    for p in &ff.signature.parameters {
        match &p.ty {
            TypeRef::Resolved(to) | TypeRef::External(to) => {
                edges.push(Dependency { from: ff.name.clone(), to: to.clone(),
                    kind: DependencyEdgeKind::UsesParamType });
            }
            _ => {}
        }
    }

    // 2. Tipo di ritorno → UsesReturnType
    match &ff.signature.return_type {
        TypeRef::Resolved(to) | TypeRef::External(to) => {
            edges.push(Dependency { from: ff.name.clone(), to: to.clone(),
                kind: DependencyEdgeKind::UsesReturnType });
        }
        _ => {}
    }

    // 3. Corpo → delega a add_block_edges
    if let Some(body) = &ff.body {
        add_block_edges(ff, body, edges);
    }
}
Cambio architetturale: In precedenza, add_function_edges accedeva direttamente ai campi ff.calls e ff.instantiates della Function. Ora la struttura Function contiene un campo body: Option<Block>, e le chiamate, le istanziazioni e le dichiarazioni locali risiedono nei Block annidati. Questo riflette più fedelmente la struttura reale del codice (blocchi if, while, ecc.).

7.5 add_block_edges — Attraversamento ricorsivo dei blocchi

Riferimento: graph.rs:137-165

Questa nuova funzione attraversa ricorsivamente la struttura a blocchi del corpo di una funzione, generando archi per dichiarazioni locali, chiamate e istanziazioni a qualsiasi livello di annidamento:

fn add_block_edges(ff: &Function, block: &Block, edges: &mut Vec<Dependency>) {
    // 1. Dichiarazioni (variabili locali) → UsesFieldType
    for decl in &block.declarations {
        if let Some(to) = type_ref_target(&decl.ty) {
            edges.push(Dependency {
                from: ff.name.clone(),
                to: to.clone(),
                kind: DependencyEdgeKind::UsesFieldType,
            });
        }
    }

    // 2. Chiamate → Calls
    for call in &block.calls {
        match call {
            TypeRef::Resolved(to) | TypeRef::External(to) => {
                edges.push(Dependency { from: ff.name.clone(), to: to.clone(),
                    kind: DependencyEdgeKind::Calls });
            }
            _ => {}
        }
    }

    // 3. Istanziazioni → Instantiates
    for inst in &block.instantiates {
        match inst {
            TypeRef::Resolved(to) | TypeRef::External(to) => {
                edges.push(Dependency { from: ff.name.clone(), to: to.clone(),
                    kind: DependencyEdgeKind::Instantiates });
            }
            _ => {}
        }
    }

    // 4. Ricorsione nei sotto-blocchi (if, while, for, ecc.)
    for sub in &block.sub_blocks {
        add_block_edges(ff, sub, edges);
    }
}

La struttura Block rappresenta un blocco di codice e contiene:

  • declarations — variabili locali dichiarate nel blocco
  • calls — chiamate a funzione effettuate nel blocco
  • instantiates — istanziazioni di tipi nel blocco
  • sub_blocks — blocchi annidati (corpi di if, while, for, ecc.)
Attribuzione al livello funzione: Tutti gli archi generati da add_block_edges, a qualsiasi livello di annidamento, sono sempre attribuiti alla funzione contenitrice (from: ff.name). Questo è intenzionale: nel grafo delle dipendenze architetturali, il livello di dettaglio minimo è la funzione, non il singolo blocco. Se una variabile viene dichiarata dentro un if, l'arco avrà come sorgente la funzione che contiene quell'if.

Diagramma: struttura IR di una Function con Block

Function "calcola" ├── signature │ ├── parameters: [p: Resolved(Veicolo)] │ └── return_type: Resolved(Auto) └── body: Block ├── declarations: [tmp: Resolved(Motore)] ├── calls: [Resolved(Veicolo::accelera)] ├── instantiates: [Resolved(Auto)] └── sub_blocks: └── Block (if branch) ├── declarations: [] ├── calls: [Resolved(log)] ├── instantiates: [] └── sub_blocks: []

In questo esempio, add_block_edges visita il blocco principale e il sotto-blocco del ramo if, generando archi per tutte le dipendenze, attribuiti sempre a "calcola".

7.6 add_impl_edges — Archi degli impl blocks

Riferimento: graph.rs:162-199

fn add_impl_edges(ib: &ImplBlock, edges: &mut Vec<Dependency>) {
    // 1. impl_for → Implements
    match &ib.impl_for {
        TypeRef::Resolved(to) | TypeRef::External(to) => {
            edges.push(Dependency { from: ib.name.clone(), to: to.clone(),
                kind: DependencyEdgeKind::Implements });
        }
        _ => {}
    }

    // 2. implements_trait → Implements
    match &ib.implements_trait {
        Some(TypeRef::Resolved(to)) | Some(TypeRef::External(to)) => {
            edges.push(Dependency { from: ib.name.clone(), to: to.clone(),
                kind: DependencyEdgeKind::Implements });
        }
        _ => {}
    }

    // 3. Metodi → NestedIn + archi funzione
    for m in &ib.methods { ... }

    // 4. Tipi annidati → NestedIn + ricorsione
    for nested in &ib.nested_types { ... }
}

Genera archi Implements sia per il tipo target (impl_for) che per l'eventuale trait (implements_trait). Poi processa metodi e tipi annidati come in traverse_structured_type_edges.

Nota: Nella pratica corrente, dopo la Fase 2 il campo module.impl_blocks è sempre vuoto (gli impl blocks vengono fusi nei tipi target). Tuttavia, add_impl_edges viene comunque chiamata preventivamente — se in futuro il flattening venisse modificato, gli archi sarebbero generati correttamente.

8. Esportazione Cytoscape e Nodi Composti (Compound Nodes)

Riferimento: export/cytoscape.rs

Il formato Cytoscape è uno standard per la visualizzazione interattiva di grafi. L'esportazione trasforma il DependencyGraph in un array JSON di elementi Cytoscape, sfruttando la funzionalità dei Compound Nodes (nodi che contengono altri nodi) per rappresentare la gerarchia.

8.1 Formato di output

Ogni elemento è un nodo o un arco. I nodi possono avere una proprietà parent:

// Nodo Modulo (Padre)
{ "data": { "id": "src::core", "label": "core", "type": "Module" } }

// Nodo Struct (Figlio)
{ "data": { "id": "src::core::Veicolo", "label": "Veicolo", "type": "Struct", "parent": "src::core" } }

// Arco (Dipendenza architetturale)
{ "data": { "id": "e0", "source": "src::core::Auto", "target": "src::core::Veicolo",
            "label": "UsesFieldType" } }

8.2 Processo di esportazione

  1. Analisi degli archi strutturali: Prima di esportare, il sistema analizza tutti gli archi di tipo ModuleContainment e NestedIn per mappare le relazioni genitore-figlio.
    • Se il nodo padre è "root", la parentela viene ignorata. Questo evita che l'intero grafo venga racchiuso in una scatola gigante e inutile, migliorando il layout.
  2. Nodi: Per ogni Component nel grafo, crea un nodo Cytoscape con:
    • id — Il QualifiedName unito con :: (es. "src::core::Veicolo")
    • label — L'ultimo segmento del nome (es. "Veicolo")
    • type — Il tipo di componente ("Module", "Struct", "Class", "Function")
    • parent — L'ID del nodo genitore (se presente e non root)
  3. Archi: Per ogni Dependency, crea un arco con source e target.
    • Gli archi ModuleContainment e NestedIn vengono scartati, poiché la loro informazione è già stata convertita nella gerarchia parent dei nodi.
    • Se il source o target non esiste come nodo (es. dipendenze esterne), viene creato automaticamente come nodo di tipo "External".
    • Archi duplicati (stessa sorgente, stesso target, stesso tipo) vengono deduplicati.
Vantaggio dei Compound Nodes: Trasformare le dipendenze gerarchiche in proprietà parent (invece di usare frecce tradizionali) permette agli algoritmi fisici come fcose di disegnare scatole (bounding boxes) per i moduli e le classi. Gli archi visibili rimangono solo quelli puramente architetturali (dipendenze di tipo e di comportamento), riducendo drasticamente il disordine visivo.

9. Generazione del Summary

Riferimento: export/summary.rs

Il quarto ed ultimo step della pipeline produce un AnalysisSummary con statistiche aggregate:

pub struct AnalysisSummary {
    pub total_modules: usize,
    pub total_structured_types: usize,
    pub total_free_functions: usize,
    pub resolved_refs: usize,
    pub unknown_refs: usize,
}

La funzione build_analysis_summary attraversa ricorsivamente tutti i moduli contando:

  • Moduli: Numero totale (inclusi sotto-moduli)
  • Tipi strutturati: Numero totale (inclusi nested types, contati ricorsivamente)
  • Funzioni libere: Numero totale (i metodi non vengono contati qui)

9.1 Conteggio ricorsivo dei riferimenti nelle funzioni

Il conteggio dei riferimenti risolti e non risolti (resolved_refs / unknown_refs) segue la stessa struttura ricorsiva a blocchi utilizzata nella generazione degli archi:

fn count_refs_in_func(f: &Function, resolved: &mut usize, failed: &mut usize) {
    // Parametri e tipo di ritorno...
    for p in &f.signature.parameters { tally_ref(&p.ty, resolved, failed); }
    tally_ref(&f.signature.return_type, resolved, failed);

    // Corpo: delega a count_refs_in_block
    if let Some(body) = &f.body {
        count_refs_in_block(body, resolved, failed);
    }
}

fn count_refs_in_block(block: &Block, resolved: &mut usize, failed: &mut usize) {
    for decl in &block.declarations { tally_ref(&decl.ty, resolved, failed); }
    for call in &block.calls         { tally_ref(call, resolved, failed); }
    for inst in &block.instantiates   { tally_ref(inst, resolved, failed); }
    // Ricorsione nei sotto-blocchi
    for sub in &block.sub_blocks {
        count_refs_in_block(sub, resolved, failed);
    }
}
Coerenza con il grafo: Il conteggio del summary e la generazione degli archi attraversano la stessa struttura a blocchi con la stessa logica ricorsiva. Questo garantisce che le statistiche del summary siano sempre coerenti con il numero di archi effettivamente generati nel grafo.
